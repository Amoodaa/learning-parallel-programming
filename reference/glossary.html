Glossary

The words every lesson uses, with one meaning each.

Terms are added as lessons cover them. Where the slides use several words for the same thing, this page picks one.

Threads

Process
A running program with its own private memory space. Contains one or more threads.
Thread
One path of execution inside a process. It has its own stack and shares the process's heap with the other threads.
Avoid: “lightweight process”, “task” (task means something else once thread pools arrive)
Main thread
The thread the JVM creates to run main(). Every program has one.
Start
Calling start(), which creates a new thread that runs the object's run(). Calling run() directly does not start anything.
Join
Calling t.join(): the current thread waits until thread t terminates.
Avoid: “wait for” as a technical term (wait() is a different method, coming in a later lecture)
Asynchronous procedure
A thread that computes a result and exposes it through a method like getResult(), to be read after a join (Deck 1 s75).
Scheduler
The part of the OS/JVM that decides which thread runs on which core, and for how long.
Concurrent
Two threads are concurrent if their executions can overlap, so either could run first (Deck 1 s9).
Parallel
Two threads are parallel if they are actually executing at the same instant, on different cores. Parallel implies concurrent, not the other way round.
Sleep
Thread.sleep(ms): pauses the current thread for a time. Static, whatever object you call it on.
Interrupt
A signal from one thread asking another to stop what it's doing. A sleeping thread receives it as an InterruptedException.
Thread state
One of NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED, returned by getState().
Stop flag
A volatile boolean field that a thread's run() loop checks, and that another thread sets to end it cleanly.
Volatile
A field modifier guaranteeing that a write by one thread is visible to later reads by other threads. Gives visibility, not mutual exclusion.
Non-deterministic
The same program, with the same input, can produce different output on different runs, because the scheduler interleaves threads differently.

Sharing & deadlock

Critical section
Code that uses a shared resource and must not be run by more than one thread at a time.
Mutual exclusion
The guarantee that at most one thread is inside a given critical section.
Race condition
A bug where the result depends on how threads happen to interleave, e.g. two unsynchronised count++.
Avoid: “sharing violation” (the slides' term for the same thing)
Atomic
Happens as one indivisible step that no other thread can see half-done. count++ is not atomic.
Deadlock
A set of threads, each waiting for an event that only another thread in the set can cause.
Coffman conditions
Mutual exclusion, hold and wait, no pre-emption, circular wait. All four are needed for deadlock.
Starvation
One thread waits forever while the others keep making progress.
CPU-bound / I/O-bound
A thread that spends its time computing / waiting on disk, network or a user.

Splitting & pools

Fair split
Boundaries index[j] = j*N/k for j = 0..k; thread j gets [index[j], index[j+1]). Pieces differ in size by at most 1 (D2 s22–24). Lesson 4.
availableProcessors()
How many processors the JVM can use: the right thread count for CPU-bound work (D2 s14, 26).
Thread pool
A fixed set of threads that take tasks from a shared queue, run them, and come back for more (D2 s44–45). Lesson 5.
ExecutorService
Java's pool type. Made by Executors.newFixedThreadPool(k); submit queues a task, shutdown lets it finish and end.
Callable<V>
A task whose call() returns a V and may throw. Runnable is the version that returns nothing.
Future<V>
Returned by submit. get() waits for the task, then returns its result: join() and getResult() in one.
Uneven work
Equal-sized pieces that take different times (large primes cost more), so some threads finish early and sit idle (D2 s77). Fix: many small tasks in a pool (s78). Lesson 6.
Fork/Join
A task that solves small problems directly and otherwise splits itself, forks the parts, joins them and combines the results (D2 s80). Lesson 7.
RecursiveTask<V> / RecursiveAction
Fork/Join task types; override compute(), which returns a V / nothing.
Work stealing
Each ForkJoinPool thread has its own task queue; a thread with nothing left takes tasks from another's queue (D2 s82).

Locks & safe sharing

Lock (intrinsic)
Every object has one. synchronized (obj) { … } lets one thread at a time hold it; others wait (D3 s5). Lesson 8.
Synchronized method
Locks this for the whole body; a static one locks the class object, e.g. Counter.class (D3 s21, s38).
Compound action
Several steps that must happen as one, like check-then-act or read-modify-write (count++) (D3 s27).
Class invariant
A rule that must always hold between fields, e.g. x == y; updates to them must be atomic together (D3 s28).
Visibility
Whether a write by one thread is seen by others. Guaranteed by taking the same lock, or by volatile (D3 s30–32). Lesson 9.
Reentrant
A thread holding a lock can take it again, e.g. one synchronized method calling another on the same object (D3 s44).
Monitor
Data plus a lock giving one thread at a time access, plus a queue of threads waiting to enter. A Java object with synchronized methods is one (D3 s48).
Immutable
Can't change after construction (final class, private final fields, no setters), so safe to share without locks (D3 s55). Lesson 10.
Leaked reference
Handing out a reference to internal mutable data, which callers can then change outside the lock. Fix: copy in, copy out (D3 s58–59).
Coarse- / fine-grained locking
One lock for the whole structure / a lock per part, e.g. locks[j]. Fine allows more concurrency but risks deadlock (D3 s62).
Resource ordering
Every thread takes locks in the same fixed order, which breaks circular wait (D3 s70). Lesson 11.
Livelock
Threads aren't blocked but keep reacting to each other and make no progress (D3 s76).
ReentrantLock
An explicit lock: lock(), then try { … } finally { unlock(); }. Same guarantees as synchronized, plus tryLock() and an optional fair mode (D3 s77–88).
