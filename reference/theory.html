Theory Sheet

The exam theory from all seven decks on one page.

Concurrent vs parallel D1 s8–10

TermDefinition
ParallelExecuting at the same instant. Needs at least 2 processors.
ConcurrentHas the potential to execute in parallel; the executions can overlap. Parallel ⇒ concurrent.
Three forms(1) one shared CPU · (2) many CPUs, shared memory · (3) many CPUs, distributed
SchedulerDecides which process runs and for how long when processes outnumber processors.
CPU- vs I/O-boundSpends its time computing vs waiting on devices.

Why concurrency D1 s7, 11, 19–23

Speed and scale (bigger problems, faster) · modelling independent tasks (servers, controllers) · aperiodic events (sleep until an alarm) · robustness (one thread failing needn't stop the others).

Problems D1 s24, 31

Non-determinism (hard to test) · sharing violations and race conditions · too many threads slows things down · not knowing what is atomic · mutable shared state · locking too much.

Critical section: 4 rules D1 s27

  1. No two processes inside their critical sections at the same time.
  2. No assumptions about the speed or number of CPUs.
  3. No process outside its critical section may block others.
  4. No process waits forever to enter.

Deadlock D1 s28–30

Definition (Tanenbaum): a set of processes, each waiting for an event that only another process in the set can cause.

Coffman: all four are necessary.

  1. Mutual exclusion: each resource is held by at most one process.
  2. Hold and wait: a process holds resources while requesting more.
  3. No pre-emption: only the holder can release a resource.
  4. Circular wait: a cycle of processes, each waiting on the next.

Strategies: ignore · detect and recover · dynamic avoidance · prevention (negate one condition, e.g. a fixed acquisition order breaks circular wait).

Starvation: one process waits forever while the others progress (not defined on the slides).

History D1 s32–33

1960s: CPU/device overlap · Dijkstra 1965: Cooperating Sequential Processes, semaphores, mutual exclusion, parbegin … parend · Hoare 1971 · monitors (Brinch Hansen & Hoare 1973) · Concurrent Pascal 1975.

Splitting work D2 s5, 14, 21–27, 77–82

Threads = processors for CPU-bound work: extra threads add creation and scheduling cost without speed (rank sort with 100,000 threads was slower than none). Too little work per thread and start-up costs dominate. Fair split: boundaries j*N/k, pieces differ by at most 1. Uneven work: equal-sized pieces may not be equal work, so threads idle; fix with many small tasks in a pool. Fork/Join: recursive divide and conquer in a ForkJoinPool; work stealing lets idle threads take queued tasks from busy ones.

Atomicity and visibility D3 s13–17, 30–36

Atomicity: an action happens as one indivisible step. Single reads and writes of int, boolean, char and references are atomic; x = x + 1 (load, add, store) is not. Visibility: without synchronization, there's no guarantee another thread ever sees a write (caching, reordering). A common lock gives both; volatile gives visibility only.

Safe sharing D3 s27, 50, 62, 67

Must be atomic: compound actions (check-then-act, read-modify-write) and class invariants. A shared class must be encapsulated, leak no references, and be thread-safe or immutable. Coarse-grained locking (one lock) is simple but inhibits concurrency; fine-grained (a lock per part) allows more but risks deadlock. Dangers: leaked references, inconsistent use of synchronized, mixing static and instance data, traversing shared structures.

Monitor D3 s48

Data plus a lock giving one thread at a time exclusive access, plus a queue of threads waiting to enter. Java's synchronization is based on monitors.

Deadlock in practice D3 s68–76, 87–91

Resource ordering (always lock in one global order) breaks circular wait. tryLock (give up instead of waiting while holding a lock) breaks hold and wait. Livelock: threads aren't blocked but keep reacting to each other without progress. Fair lock: new ReentrantLock(true) serves the longest-waiting thread first, preventing starvation at a cost in speed.

Condition variables D4 s2–16

A Condition belongs to a lock (lock.newCondition()). await() atomically releases the lock and sleeps; when woken it must reacquire the lock before continuing. signal() wakes one waiter, signalAll() all; a signal with nobody waiting is lost. Always await in a while loop: another thread may get the lock first and make the condition false again (and spurious wakeups are allowed). Producer/consumer: a fixed-size buffer; the producer waits while full, the consumer while empty; two conditions (notFull, notEmpty) on one lock.

Classic problems D4 s17–39, s52

Dining philosophers: 5 philosophers, 5 chopsticks, each needs both neighbours'. All taking their left at once is a deadlock (all four Coffman conditions). Fixes: allow at most n−1 to try (breaks circular wait); take both at once (breaks hold and wait); take the lower-numbered first (breaks circular wait). Readers/writers: one writer at a time, no readers while writing, no writers while reading, many readers together, writers have precedence (a waiting writer blocks new readers, so readers may starve). Bathroom: same-gender sharing; a steady stream of one gender can starve the other.

Stopping a thread D4 s40–46

t.interrupt(): a running thread only has its interrupted status set and must poll isInterrupted(); a thread blocked in sleep/join/await gets an InterruptedException. Either way the thread stops itself. Suspend/resume: the thread checks a volatile flag at a safe point and awaits a condition until resumed.

Semaphore D5 s2–23

A counter of permits with atomic acquire() (take one, or block while 0) and release() (add one, waking a waiter). Starting value decides the use: 1 = binary semaphore = lock; 0 = signal (TB acquires, TA releases: TA goes first; two of them = rendezvous); n = at most n at once (tunnel). Unlike a lock, permits have no owner; any thread may release. A semaphore with n > 1 gives no mutual exclusion, so shared data still needs a lock or atomic. Don't acquire() while holding a lock the releaser needs (s19 deadlock).

Latch, barrier, blocking queue D6 s2–32

CountDownLatch(n): await() blocks until countDown() has been called n times; one-use. CyclicBarrier(n): each of n threads' await() blocks until all n arrive, then all go and it resets; an optional barrier action runs once per trip, before release. ArrayBlockingQueue: a ready-made bounded buffer; put blocks while full, take while empty. Stop k consumers with k sentinel values. Thread pool life cycle (s33–34): workers repeatedly take a task from the shared queue, run it, and wait for the next; created once and reused, which saves servers creating a thread per request.

Lock-free D7 s2–35

Non-blocking: failure or suspension of one thread can't cause failure or suspension of another. Lock-free: at each step some thread makes progress. Locking is pessimistic (always locks); lock-free is optimistic (update, detect collision, retry). CAS(location, expected, new) atomically writes only if the location still holds expected, returning true/false; used in a read–compute–CAS–retry loop. Pros: no deadlock, no priority inversion, fast at realistic contention. Cons: busy retrying under high contention, CPU cost, hard to write, needs hardware CAS. Atomic classes protect one variable, not invariants between several. A spin lock built from AtomicBoolean is still a lock, not non-blocking.
