Course map

Seven short lessons. Follow them in order.

  1. Start and joinMake a thread, wait for it, read its result.
  2. Living threadsSleep, thread states, and stopping with a flag.
  3. Theory packConcurrency, critical sections, and deadlock.
  4. Fair splittingDivide work fairly; use one thread per core.
  5. Thread poolsSubmit tasks and get results with a Future.
  6. Uneven workUse small tasks so workers don't sit idle.
  7. Fork/Join PlannedSplit tasks recursively and combine results.

Lessons 1–3 cover Deck 1. Lessons 4–6 cover Deck 2 up to slide 78; lesson 7 (Fork/Join) is still to come. Only the two decks below are in scope.

Deck 2 · slide guide

Download Elementary parallelism slides. Split work, measure it, then fix the bottlenecks.

Lesson 4: slides 2–41 · Lesson 5: 43–72 · Lesson 6: 73–78 · Lesson 7: 79–99. Slide 1 is the title; slide 42 is a divider.

  1. Split, start, join, combine (slides 2–7). Two threads search two halves of an array. Problem: with 100 elements, creating the threads costs more than the search itself (5). A shared Found object lets one thread tell the other to stop early (6–7).
  2. It really is faster (8–13). Two threads selection-sort the two halves, then main merges them. About 4× faster on 2 cores.Why 4× and not 2×? Selection sort costs ~n² steps. Two halves cost 2·(n/2)² = n²/2, which is already half the work, and running them at the same time halves it again. (This explanation is mine, not the slides'.) Also, slide 13 says 100 000 values but slide 10's code uses 1 000 000.
  3. How many threads? (14) As many as there are cores. More than that doesn't help CPU-bound work.
  4. Too many threads is slower (15–21). Rank sort with one thread per element means 100 000 threads, which was slower than having no threads at all.
  5. Fair split (22–27). Use k = number of cores and boundaries index[j] = j*N/k, so the pieces differ in size by at most 1. That got about 2× on 2 cores and about 8× on 8.
  6. Same recipe, bigger job (28–41). Happy numbers is just a CPU-heavy problem to practise the split on: 420 s down to 159 s.
  7. Thread pools (43–66). Stop creating threads yourself. Create a fixed pool once and submit tasks to it. Runnable returns nothing; Callable returns a value through a Future, and future.get() waits for it like join().
  8. Sum with a pool (67–72). The fair split from step 5, rewritten with Callable.
  9. Uneven work (73–78). Counting primes: large numbers take longer to test, so equal-sized pieces are not equal work and some threads sit idle (only 33% gain). Fix: many small pieces (e.g. 1000 each) in a pool, so a thread that finishes early takes another piece.
  10. Fork/Join (79–99). The task splits itself recursively until it's small (RecursiveTask / RecursiveAction, compute(), fork(), join()). Idle threads steal queued pieces from busy ones ("work stealing"). Examples: array sum and quicksort.

Read top to bottom, this is the course's main skill: split work fairly, use the right number of threads, wait for the results, combine them. Everything in Deck 1's Thread API section exists to support it.
