Thread-Safe Classes

Design a class that stays safe however it's shared: don't leak references, prefer immutable objects, and choose how big each lock should be.

Your win today: you'll give an array one lock per element and see it run about 7× faster than one lock for the whole array, with the same correct total. About 20 minutes.

Deck 3 slides 50–67 are one long example (a library of books) followed by a speed comparison (a shared array). The library answers “what can still go wrong after every method is synchronized?” The array answers “how much should one lock cover?”

1 · The rule

Deck 3 · slide 50

A class that is shared between threads must be properly encapsulated, must not leak references to its internal data, and each object it hands out must be either thread-safe or immutable. The rest of the library example shows each of these.

2 · The leak

Deck 3 · slides 51–54

Slides 51–53's Library keeps its books in a private ArrayList and makes every method synchronized. That looks safe. But get(title) returns the actual Book object stored inside the list. The caller now holds a reference to the library's internal data, and can use it outside the library's lock. If Book can be changed, the lock no longer protects it. Slide 54 asks the question: should Book be immutable, or thread-safe?

3 · Option A: make it immutable

Deck 3 · slides 55–56

final class Book implements Comparable<Book> {
    private final String title;
    Book(String t) { title = t; }
    public String title() { return title; }
    // equals, hashCode, compareTo use title
}

An immutable object can't change after construction, so any number of threads can read it with no lock at all. Nothing to race on, nothing to go stale. The recipe:

  • final class: nobody can write a mutable subclass.
  • private final fields, set once in the constructor.
  • No setters.

The equals and hashCode methods on slides 55–56 aren't about threads. ArrayList.contains and indexOf use equals to find a book by title. (Slide 55's if(!(p instanceof Book) is missing a ); see the errata.)

Oracle's rules for immutable objects are the same list, plus one more: if a field refers to a mutable object (an array, say), never hand that object out. A Strategy for Defining Immutable Objects

4 · Option B: copy in, copy out

Deck 3 · slides 57–61

If books must be editable, slide 57's Book synchronizes its own title() and set(). Then the library stops handing out its internal objects:

  • add stores a copy of the book it was given (slide 58), so the caller's object isn't the one inside.
  • get returns a copy (slide 59), so the caller can't reach the stored one.
  • Editing happens through the library's own synchronized editBk (slide 60), inside its lock.

This is called defensive copying. Outside code never gets a reference to the library's data, so the library's lock covers every change.

5 · Coarse or fine

Deck 3 · slides 62–66

Slide 62 names the trade-off:

Coarse-grained (s63)Fine-grained (s64–66)
LocksOne: synchronized methods lock the whole objectOne per element: locks[j]
ConcurrencyOne thread at a time, even on different elementsThreads on different elements run together
RiskSimple, hard to get wrongMore code; an action needing two locks can deadlock (lesson 11)
public void inc(int j, int x) {
    synchronized (locks[j]) {   // only element j
        data[j] = data[j] + x;
    }
}

With 8 threads updating random elements of a 1,000-element array, the coarse version took about 1.4 s on my machine and the fine version about 0.2 s, with identical totals.

6 · Dangers when sharing

Deck 3 · slide 67

Slide 67 is a checklist for the exam and the assignment:

  • Leaking references to internal data (sections 2–4).
  • Inconsistent use of synchronized: one unlocked method breaks the protection (lesson 8).
  • Mixing static and instance data: two different locks (lesson 9).
  • Traversing a list while another thread changes it. The slides give no detail; the safe default is to hold the lock for the whole traversal.

Check yourself

Answer from memory, without scrolling up. You get one click per question.

Every Library method is synchronized, but get returns the stored mutable Book. What's wrong?

The lock only covers code inside the library's methods. Once a caller holds the internal Book, it can change it at any time with no lock. That's a leaked reference.

Why can many threads read an immutable Book without any lock?

Races need someone writing. An immutable object is only written in its constructor, so after that every thread just reads the same value.

What is the main cost of fine-grained locking?

Fine-grained locking gives more concurrency. The price is more locks to manage, and an operation that needs two of them (such as swapping two elements) can deadlock. That's lesson 11.

Slide 59's get returns new Book(b.title()) rather than b. Why?

Defensive copying: the caller gets its own Book, and changing it doesn't affect the library. All changes to stored books go through the library's synchronized editBk.

Stretch: break it on purpose

(a) Leave out the lock in inc entirely. Is it faster? Is the total right? (b) Use synchronized (this) instead of locks[j]. What does the program say, and why?

Solution (only after trying) 
void inc(int j, int x) {
    synchronized (locks[j]) {
        data[j] = Slow.add(data[j], x);
    }
}

int get(int j) {
    synchronized (locks[j]) { return data[j]; }
}

(a) A little faster, but my runs lost about 450 of 80,000 updates: two threads hit the same element at the same moment. (b) this is one lock for the whole array, which is coarse-grained again, so the program reports it isn't faster.

Exam practice

Compare coarse-grained and fine-grained locking, with an example of each. (4 marks)

Coarse-grained: one lock protects the whole data structure, e.g. a shared array whose methods are all synchronized. It is simple and safe, but only one thread can use the structure at a time, even when threads access different elements, so it inhibits concurrency. Fine-grained: separate locks protect separate parts, e.g. an array of lock objects with synchronized(locks[j]) around each access to element j. Threads using different elements proceed in parallel, giving more concurrency, at the cost of more complexity and the risk of deadlock when an operation needs several locks.

Marks are my estimate, not taken from your exam.
