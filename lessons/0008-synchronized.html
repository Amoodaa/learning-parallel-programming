Synchronized

Lock shared data so only one thread at a time can use it, and fix lesson 3's lost updates.

Your win today: you'll make a counter and a pair of fields thread-safe, and watch a count that came out as 770,737 come out as exactly 1. About 25 minutes.

This is the first lesson from Deck 3, Sharing Resources. Decks 1 and 2 gave each thread its own data. Deck 3 is about threads that must share, like lesson 3's Race.java, which lost about half its updates.

1 · Interference

Deck 3 · slides 2–4

Slides 3–4 start two Messenger threads printing to the same screen, and slide 2 warns the output will be unreadable. On Java 26 each println line came out whole, but lines from the two threads were mixed together. Printing a line in two parts gave lines like She loves me Happy days she loves me not. The screen is shared, just like a variable.

2 · synchronized blocks

Deck 3 · slides 5–12

synchronized (lock) {
    // only one thread at a time, per lock object
}

Any object can be a lock. A thread must take the lock to enter the block, and it releases the lock when it leaves. A second thread that wants the same lock waits at the door (lesson 2's BLOCKED state). This is lesson 3's mutual exclusion: the block is a critical section.

Slides 6–7 pass one Object lock = new Object() to both Messengers, so each prints all its lines before the other starts. Slides 9–11 share one lock between two Summers and an Editor, so no sum is taken mid-edit. Slide 12 locks the array itself: synchronized (data).

A lock only works if everyone uses it (slide 8). In slide 6, main prints “Hello from main” with no lock, so its output can still appear in the middle of a Messenger's lines. And never sleep while holding a lock: everyone waiting for it sleeps too.

3 · Why x = x + 1 loses updates

Deck 3 · slides 13–19

Java guarantees that a single read or a single write of an int, boolean, char or reference is atomic: it can't be seen half-done (slide 13). But x = x + 1 is three steps (slide 17):

load x into a register
add 1 to the register
store the register back into x

Slide 18 interleaves two threads: both load x = 1, one stores 2, the other stores 0, and an update is lost. That's lesson 3's Race.java exactly.

Slide 13 says long and double take two reads and two writes. The Java spec says this only for non-volatile ones; reads and writes of volatile long and volatile double are atomic. JLS §17.7

Slide 19's fix puts each call inside synchronized (c) { c.inc(); }. It works, but every caller has to remember to do it.

4 · synchronized methods

Deck 3 · slides 20–24

Better: make the class protect itself (slide 20). A synchronized method is shorthand for locking this around the whole body (slide 21):

synchronized void inc() { x = x + 1; }
// means the same as
void inc() { synchronized (this) { x = x + 1; } }

Slide 22's Counter marks inc, dec and get all synchronized. Now every caller is safe without doing anything. The rules (slides 23–24):

  • Two threads calling synchronized methods on the same object take turns, even if they call different methods.
  • A synchronized method and a non-synchronized method on the same object can run at the same time, and may interfere. One unlocked method breaks the protection.

5 · What must be atomic

Deck 3 · slides 25–29

Slides 25–26's joint bank account shows why the lock must cover the whole action, not single lines:

synchronized boolean withdraw(double amt) {
    if (balance >= amt) {        // check...
        balance = balance - amt; // ...then act
        return true;
    }
    return false;
}

Without the lock, two people could both pass the check with £50 in the account and both take £50. Slide 27 names two things that must be atomic:

  • Compound actions such as check-then-act and read-modify-write.
  • Class invariants: rules that must always hold between fields. If x == y must always be true, then x = x + a; y = y + a; must happen as one step (slide 28), or another thread can see x updated and y not yet. Slide 29: an array and its count n are the same kind of pair.

Also from slide 27: do slow computations outside the lock where you can, so other threads wait less.

Check yourself

Answer from memory, without scrolling up. You get one click per question.

Two threads each run x = x + 1 once on a shared x = 1, with no lock. What can x end up as?

Each thread loads, adds and stores. If both load 1 before either stores, both store 2 and one update is lost. Otherwise you get 3. It can't drop to 1, because each store writes a value one higher than something read.

A class has synchronized void inc() and a plain void reset(). Thread A calls inc while B calls reset on the same object. What happens?

Slide 24: only synchronized methods take the lock, so reset never waits for it. Every method that touches the shared fields has to be synchronized.

Two Messengers use synchronized (new Object()) { … } inside run(). Does it stop their output mixing?

Threads only exclude each other when they lock the same object. That's why slide 6 creates one lock in main and passes it to both threads.

Which of these is not on slide 27's list of locking advice?

Lock what is shared, and only for as long as needed. Locking everything makes threads queue up for no reason. Lesson 10 covers how coarse or fine locks should be.

Stretch: break it on purpose

(a) Synchronize inc and dec but not get. Does the counter still come out right here? Why is it still wrong in general? (b) Put each of x's and y's updates in its own synchronized (this) block. Does part 2 pass?

Solution (only after trying) 
synchronized void inc() { x = x + 1; }   // TODO 1
synchronized void dec() { x = x - 1; }
synchronized int get()  { return x; }

synchronized (this) {                    // TODO 2
    x = x + 1;
    y = y + 1;
}

(a) Here, yes: get runs only after both joins. But a thread calling get during the updates has no visibility guarantee (lesson 9). (b) No. Between the two blocks the lock is free, and the checker can see x one ahead of y. The invariant needs both updates in one locked step.

Exam practice

Explain why count++ on a shared variable is not thread-safe, and show how to make a counter class thread-safe in Java. (5 marks)

count++ is a read-modify-write: load the value, add one, store it back. It is not atomic, so two threads can both load the same value and both store value + 1, losing one update (a race condition). Fix: make the class use its intrinsic lock by declaring every method that accesses the field synchronized (inc, dec and get). Only one thread at a time can then run a synchronized method on that object, so each increment completes before another begins. All accessing methods must be synchronized, because a non-synchronized method does not take the lock and can still interfere.

Next time, from memory

What does a synchronized method lock?

this, the object the method is called on. It's the same as wrapping the body in synchronized (this) { … }.

Name two kinds of action that must be atomic.

Compound actions (check-then-act, read-modify-write) and class invariants (fields that must stay consistent with each other).

Name the four critical-section rules. (lesson 3)

No two inside at once; no assumptions about speed or number of CPUs; nobody outside may block others; nobody waits forever.
