Semaphore Puzzles

Three bigger problems built from lesson 15's patterns: an output-ordering puzzle, a first-come-first-served queue, and a resource allocator.

Your win today: you'll make three threads print a's, b's and c's in an order that obeys three rules, using only semaphores. About 25 minutes.

Deck 5 slides 24–45 are exam-style problems. Each is solved by combining lesson 15's three uses of a semaphore: signalling ("your turn"), counting ("one more available"), and a semaphore per thread to wake it at the right moment.

1 · The a/b/c puzzle

Deck 5 · slides 24–30

TA prints a over and over, TB prints b and TC prints c. The output must satisfy (slide 24):

  1. a b is output before any c;
  2. b's and c's alternate: b, c, b, c…;
  3. at every point, the number of b's plus c's so far is at most the number of a's so far.

So abacabacaabc is allowed, but acb breaks rule 1 and aabcabc breaks rule 3 (slide 25). The slides build the answer in two steps, one rule at a time.

Step 1: alternate b and c (slides 26–27). This is "taking turns", like a rendezvous that repeats. Two semaphores pass the turn back and forth:

// TB: semC.acquire(); print('b'); semB.release();
// TC: semB.acquire(); print('c'); semC.release();

TB waits on semC ("c has just been printed"), so to let b go first (rule 1), semC must start at 1 and semB at 0. The slides never show the starting values.

Step 2: count the a's (slides 28–30). TA releases semA after every a, so semA counts a's that haven't been "used" yet. TB and TC each acquire one before printing (slide 29), which enforces rule 3:

// TA: print('a'); semA.release();
// TB: semC.acquire(); semA.acquire();
//     print('b'); semB.release();

Slide 30 shows TB. TC is the mirror image and isn't shown.

2 · A queue of threads

Deck 5 · slides 31–35

Threads should be let through in order of arrival. A plain semaphore makes no promise about which waiting thread a release wakes (slide 3 says "e.g., at random"). The trick (slide 31): every thread waits on its own semaphore, which starts at 0, and a queue remembers the order.

void join(Semaphore sem) {          // slide 32
    lock.lock();
    try { queue.add(sem); }          // remember my place
    finally { lock.unlock(); }
    sem.acquire();           // + try; wait for my turn
}
void next() {                        // slide 33
    lock.lock();
    try {
        if (queue.size() > 0) queue.poll().release();
    } finally { lock.unlock(); }
}

Because each thread has its own semaphore, release() wakes exactly the thread at the head of the queue. Notice that join unlocks before it calls acquire(). If it waited while holding the lock, next() could never get in to release it: slide 19's deadlock again. Slide 35's main starts 10 threads and calls next() once a second. (In main, the threads may join the queue in a different order from the order they were started, so "turn" numbers can come out of order.)

3 · A resource allocator

Deck 5 · slides 36–45

There's a fixed number of identical resources. A client asks for k of them at once, gets all k together, and requests are served first come, first served (slide 36). It uses the thread queue's idea: each Request holds the number wanted and its client's own semaphore, and allocate() releases it (slide 37).

  • getResources(req) (slides 39–40): if the request is bigger than the total, it throws. If anyone is already queued, the request joins the queue even if there are enough resources free. Otherwise, if enough are free, they're granted straight away, and if not, it queues.
  • returnResources(n) (slides 41–42): add n back, then serve requests from the head of the queue while the head one fits.
  • The client (slides 43–45) creates a request, calls getResources, then acquire()s its own semaphore. That returns at once if the request was granted, and otherwise waits until returnResources grants it.

Why does a small request wait behind a big one, even when it would fit? That's what first come, first served means. If small requests could overtake, a large request might never collect enough resources: it would starve. The cost is that resources sit idle while the head of the queue waits.

Two slide errors. Slide 39 declares getResources(...) throws Exception, but slide 44 calls it without a try/catch, so it won't compile. And slide 44 calls resources.getMax(), which slide 38's class doesn't define. It needs int getMax() { return maxResources; }.

Check yourself

Answer from memory, without scrolling up. You get one click per question.

In the a/b/c puzzle, what does semA's count mean?

TA adds one per a, and each b or c takes one. It can't go below 0, so b's + c's can never overtake the a's (rule 3).

For b to come first, what must semB and semC start at? (TB waits on semC, TC on semB.)

TB needs a permit on semC to print the first b. Both 0 would deadlock, and both 1 would let a c out first.

Why does the thread queue give each thread its own semaphore, instead of all waiting on one?

A release on a shared semaphore wakes some waiting thread, with no guaranteed order. Releasing the head's own semaphore picks exactly who goes next, which gives arrival order.

The allocator has 5 free. The head of the queue wants 8, and a new request wants 2. What happens to the new request?

If anyone is queued, new requests queue too (slide 39). That's first come, first served, and it keeps big requests from starving.

Exam practice

Explain how the thread queue (slides 31–35) releases threads in order of arrival. (4 marks)

Each thread creates its own semaphore with 0 permits. It adds the semaphore to a shared FIFO queue under a lock, releases the lock, and then calls acquire() on its own semaphore, so it blocks. The controller's next() removes the semaphore at the head of the queue, under the lock, and releases it. That wakes exactly the thread that joined first. Order is guaranteed by the queue, not by the semaphore. The lock is released before blocking so that next() can run.

Give the three output rules of the a/b/c problem and say which semaphore enforces each. (6 marks)

Rule 1, b before any c: semC starts at 1 and semB at 0, so only TB can print first. Rule 2, b and c alternate: TB waits on semC and releases semB, and TC does the opposite, so the turn passes back and forth. Rule 3, b's + c's ≤ a's: TA releases semA after every a, and TB and TC each acquire semA before printing. Its count can't go below zero, so b's and c's can't overtake the a's.

Marks are my estimate, not taken from your exam.
