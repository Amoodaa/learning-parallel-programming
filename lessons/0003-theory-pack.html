Deck 1 scatters its theory: slides 5–33 jump from quotes to definitions to code to history. Sorted out, it's four ideas, each building on the last: what concurrency is, why we bother, what goes wrong when threads share things, and the worst case of that, deadlock.

1 · Concurrent vs parallel

Deck 1 · slides 8–10

Slide 8 lists three ways to run several processes:

  1. All share one processor, taking turns.
  2. Each has its own processor, with shared memory (a multicore PC; Java threads).
  3. Each has its own processor, distributed across machines (the MPI half of the course).

Then slide 9 gives the two definitions the exam is most likely to ask for:

  • Parallel: actually executing at the same instant. Only possible in forms 2 and 3.
  • Concurrent: having the potential to execute in parallel. Two threads on a single core are concurrent but not parallel, because they take turns.

So parallel implies concurrent, but not the other way round. When there are more threads than cores, the scheduler decides who runs and for how long (slide 10). A thread is CPU-bound if it spends its time computing, and I/O-bound if it spends its time waiting on disk, network or a user. The difference matters in Deck 2: extra threads help CPU-bound work only up to the number of cores.

3 · What goes wrong: sharing

Deck 1 · slides 24–27, 31

Non-determinism (slide 24): a single-threaded program gives the same output every run. A multithreaded one can give different output on each run, because the scheduler interleaves the threads differently every time. That's why testing is hard: one passing run proves little.

It gets dangerous when threads share data. A critical section is a piece of code that uses a shared resource (slides 25–26: the screen) and must not be run by two threads at once. Slide 27 lists the four rules any correct solution must satisfy:

  1. Mutual exclusion: no two inside their critical sections at the same time.
  2. No speed assumptions: it must work whatever the speed or number of CPUs.
  3. Outside can't block: a thread outside its critical section may not stop others entering.
  4. No waiting forever: every thread eventually gets in.
OSTEP: “A critical section is a piece of code that accesses a shared variable … and must not be concurrently executed by more than one thread.” A race condition is when “the results depend on the timing of the code's execution.” OSTEP ch. 26, Concurrency: An Introduction

Slide 31's bullet “What is atomic and what is not?” refers to exactly this: count++ looks like one step, but it's really three (read, add 1, write back). Two threads can both read the same old value and each write back the same +1, so one of the increments is lost. Run the demo to see it:

java lessons/code/0003/Race.java

Two threads each add 1 a million times. On my machine it printed about 1.1 million instead of 2 million, and a different number every run. Race.java is a demonstration only; the fix (locks) is a later lecture.

4 · Deadlock

Deck 1 · slides 28–30

Deadlock (Tanenbaum, slide 28): a set of processes, each waiting for an event that only another process in the set can cause. Everyone is waiting, so nobody ever moves. For example, A holds the printer and wants the scanner, while B holds the scanner and wants the printer.

Coffman: deadlock needs all four of these at once (slide 29):

ConditionIn plain words
Mutual exclusionEach resource is held by at most one process.
Hold and waitA process keeps what it has while asking for more.
No pre-emptionYou can't take a resource away; only the holder releases it.
Circular waitA cycle: A waits for B, B waits for … , which waits for A.
OSTEP lists the same four and adds: “If any of these four conditions are not met, deadlock cannot occur.” Its most practical prevention technique is a fixed lock order, which breaks circular wait. OSTEP ch. 32, Common Concurrency Problems

Four strategies for dealing with it (slide 30): ignore it; detect and recover (find the cycle, then kill or roll back a process); avoid it dynamically (only grant a resource if the system stays safe); prevent it (design so that one of the four conditions can never hold, e.g. always acquire resources in the same order).

Starvation appears in slide 28's title but is never defined. It means one thread waits forever while the others keep running, which breaks rule 4 from section 3. Under deadlock nobody runs; under starvation everyone else does.

Check yourself

Two threads run on a machine with a single core. They are…

They take turns, so they never run at the same instant (not parallel). They could run in parallel given more cores, which makes them concurrent.

“Every thread must acquire lock L1 before lock L2.” Which Coffman condition does this rule break?

If everyone takes resources in the same order, no cycle can form. Threads can still hold one lock while waiting for the other, and the locks are still exclusive and can't be taken away.

Thread A has left its critical section, but it's still holding a flag that stops B from entering. Which rule from slide 27 is broken?

Rule 3: a thread outside its critical section must not stop others from entering. Only one thread is involved here, so mutual exclusion is fine.

Race.java printed 1,112,159 instead of 2,000,000. Why?

count++ is read, add, write. When both threads read the same value and both write back value+1, one increment is lost. The joins are correct, and 2 million is far below int's limit of about 2.1 billion.

The OS spots a cycle of waiting processes and kills one of them. Which strategy is that?

The deadlock was allowed to happen, then found (detection) and broken (recovery). Prevention and avoidance stop it from happening in the first place.

Now do it: exam answers

Practise these the way the exam will ask them. Write each answer on paper or in a text file before opening the model answer, then mark yourself. Recalling it is what makes it stick; reading it back doesn't.

Q1. Define concurrent and parallel, with an example where they differ. (3 marks)

Parallel: two processes are executing at the same instant, which needs more than one processor. Concurrent: two processes have the potential to execute in parallel; their executions can overlap in any order. Example: two threads on a single-core CPU are concurrent (interleaved by the scheduler) but not parallel.

Q2. State the four conditions for correct sharing via critical sections. (4 marks)

(1) No two processes inside their critical sections at the same time. (2) No assumptions about the speed or number of CPUs. (3) No process outside its critical section may block another. (4) No process waits forever to enter its critical section.

Q3. Define deadlock, list Coffman's four conditions, and give one prevention technique. (6 marks)

Deadlock: a set of processes, each waiting for an event that only another process in the set can cause. Conditions: mutual exclusion, hold and wait, no pre-emption, circular wait. All four are necessary. Prevention: impose a global order on acquiring resources, which breaks circular wait.

Q4. Give two advantages of concurrent programming and two problems it introduces. (4 marks)

Advantages (any two): solves larger problems faster using more CPUs and memory; models systems of independent tasks naturally (servers, embedded controllers); responds to aperiodic events; robustness, since one failed thread needn't stop the others. Problems (any two): non-determinism makes testing hard; race conditions on shared data; deadlock and starvation; too many threads can slow a program down.

Marks are my estimate of a typical split, not taken from your exam. For real exam format, past papers are the best source; ask your lecturer if any exist.
