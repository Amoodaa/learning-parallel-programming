Deadlock and Lock

When an action needs two locks, take them in a fixed order. Then meet ReentrantLock, the explicit version of synchronized.

Your win today: you'll take a shuffle program that deadlocks every time and make it finish, by changing how two locks are chosen. About 20 minutes.

Deck 3 slides 68–91 bring back lesson 3's deadlock theory, this time in real code. Lesson 10's fine-grained locks are fast, but a swap needs two of them, and two locks can deadlock. The slides fix it twice, first with lock ordering and then with tryLock. Slides 92–101 are practice; this lesson ends with them.

1 · Deadlock, now in code

Deck 3 · slides 68–75

Slides 68–69 repeat lesson 3: two threads are deadlocked if each holds a resource the other is waiting for, and it needs all four Coffman conditions. Slide 70's prevention is resource ordering: every thread requests resources in the same fixed order, which makes a circular wait impossible.

Slides 71–75 apply it. Several threads shuffle an array by swapping random pairs. A swap must be atomic, and with one lock per element (lesson 10) it needs both elements' locks:

// thread A: swap(3, 7)      thread B: swap(7, 3)
synchronized (locks[3]) {    synchronized (locks[7]) {
  synchronized (locks[7]) {    synchronized (locks[3]) {

A holds 3 and waits for 7; B holds 7 and waits for 3. That's a circular wait, and neither will ever move. Slide 74's fix is to always pick left < right and lock left first. Then both threads try lock 3 first, one of them waits before holding anything, and no cycle can form.

I ran 4 threads doing 200,000 random swaps each on a 10-element array. Locking in the caller's order deadlocked within 5 seconds in 3 runs out of 3. Locking the lower index first finished every time in under a second.

2 · Starvation and livelock

Deck 3 · slide 76

Slide 76 only has the two words, so here are the definitions:

  • Starvation: a thread can never get the resource it needs, because others keep taking it. The other threads still make progress (lesson 3).
  • Livelock: threads aren't blocked, but they keep reacting to each other and none gets any work done. Think of two people in a corridor who both step aside the same way, again and again.
The corridor example is Oracle's: livelocked threads “are not blocked — they are simply too busy responding to each other to resume work.” Starvation and Livelock

3 · The Lock interface

Deck 3 · slides 77–82

A Lock is synchronized made explicit: you call lock() and unlock() yourself (slides 77–78). ReentrantLock gives the same guarantees as synchronized, atomicity and visibility, and like it is reentrant (slide 79). Slide 80's pattern is the one to memorise:

Lock lock = new ReentrantLock();
lock.lock();
try {
    // the critical section
} finally {
    lock.unlock();   // runs even if an exception is thrown
}

Why finally? synchronized releases its lock automatically when the block ends, even through an exception. A Lock doesn't: forget unlock() on one path and the lock is held forever. Slides 81–82 redo the shared screen this way. You need import java.util.concurrent.locks.*;.

4 · The theatre

Deck 3 · slides 83–87

Slides 83–86 book seats. getSeats() lists the free seats and bookSeat(k) books one, each inside lock()/finally unlock(). Slide 83's key sentence: a seat may appear free and be booked by someone else before you book it. That's fine, because bookSeat checks again inside the lock (if (seats[k])) before taking it. It's lesson 8's check-then-act, done right.

Fairness (slide 87): by default, when a lock is released there's no rule about which waiting thread gets it next. new ReentrantLock(true) gives it to the longest-waiting thread, which prevents starvation but is slower.

Javadoc: programs using fair locks “may display lower overall throughput (i.e., are slower; often much slower)”. ReentrantLock

5 · tryLock: don't wait

Deck 3 · slides 88–91

tryLock() takes the lock if it's free and returns true; otherwise it returns false immediately instead of waiting (slide 88). Slide 91 uses it for the shuffle:

locks[g].lock();
try {
    if (locks[h].tryLock()) {
        try { /* swap */ } finally { locks[h].unlock(); }
    }   // else: skip this swap
} finally { locks[g].unlock(); }

A thread never waits while holding a lock. That breaks hold and wait, so no deadlock is possible, in any order. The price: some swaps are skipped and have to be tried again.

Check yourself

Answer from memory, without scrolling up. You get one click per question.

Always locking the lower index first prevents deadlock by breaking which condition?

With one global order, a thread can only ever wait for a higher-numbered lock than the ones it holds, so no cycle can form (slide 70). Slide 91's tryLock breaks hold and wait instead.

Why must unlock() go in a finally block?

If the critical section throws and unlock() is skipped, the lock stays held and every other thread waits forever. finally runs however the try ends.

The theatre's getSeats() showed seat 5 free. Why must bookSeat(5) still check seats[5]?

The lock was released between the two calls, so the list can be out of date. The check and the booking must happen together inside one lock (check-then-act).

Threads are not blocked, but keep reacting to each other and make no progress. What is that?

Deadlocked threads are blocked. Livelocked threads are busy but get nowhere. A starving thread is stuck while the others progress.

Deck 3's own exercises

Deck 3 · slides 92–101

The deck ends with three programs and no questions. These are the questions they set up, with my answers.

Slides 92–93: a Summer prints the array's sum while a Swapper swaps elements. Should the printed sum change? What's wrong with stopSwap()?

No: swapping doesn't change the sum, and both lock data, so a sum is never taken mid-swap. But go isn't volatile and isn't read under a lock, so stopSwap() may never be seen (lesson 9).

Slides 94–97: Counter's field is both volatile and accessed only through synchronized methods. Is volatile needed? Can main's readings go below 0?

Not needed: the lock already gives visibility. And no, dec only decrements when the count is above 0, and the check and decrement are one atomic step inside a synchronized method.

Slides 98–101: visitors enter a garden through two turnstiles. Why are t1, t2 and leave all synchronized, when they're different methods?

They all change the same count, and all synchronized methods of one object share one lock (lesson 8). If only t1 were synchronized, a visitor entering through t2 could race with it and lose a count.

Exam practice

Explain how resource ordering prevents deadlock when swapping array elements protected by an array of locks. (4 marks)

A swap needs the locks of both elements. If threads take them in arbitrary order, one thread can hold lock i and wait for j while another holds j and waits for i: a circular wait, so deadlock. With resource ordering, every thread always locks the lower index first, then the higher. A thread holding a lock can then only wait for a higher-numbered lock, so a cycle of waiting threads is impossible. This breaks Coffman's circular-wait condition, and since all four conditions are necessary, deadlock cannot occur.

Two ways the slides prevent deadlock in the shuffle, and which condition each breaks.

Lock in a fixed order (circular wait); tryLock the second lock and give up if it's taken (hold and wait).

Coarse vs fine-grained locking in one line each. (lesson 10)

Coarse: one lock for everything; simple, less concurrency. Fine: a lock per part; more concurrency, more complexity and deadlock risk.
