Interrupts and More Signals

Stop a thread with interrupt(), pause and resume one with a condition, and solve a problem the slides leave open.

Your win today: you'll write the shared-bathroom control from slide 52, which has no solution in the slides. About 25 minutes.

Deck 4 slides 40–56 are a mixed bag. The first two programs control a thread from outside: stopping it (slides 40–42, a better way than lesson 2's flag) and pausing it (slides 43–46). The rest are more problems built from lesson 12's lock-and-condition pattern.

1 · Stopping a thread with interrupt()

Deck 4 · slides 40–42

In lesson 2 you stopped a thread with a volatile boolean flag. That has a weak spot: a thread that is asleep or waiting doesn't look at the flag until it wakes up. Slide 40's main uses the built-in alternative instead, t.interrupt(). What happens depends on what the thread is doing at that moment:

  • It's running (slide 41): nothing happens by itself. Java sets the thread's interrupted status, and the thread has to check it with isInterrupted() and stop on its own.
  • It's blocked in sleep, join or await (slide 42): the call ends early by throwing InterruptedException, and the status is cleared. The thread decides what to do in its catch.
// slide 41: a busy thread polls the flag
while (true) {
    // do some work
    if (isInterrupted()) return;
}

// slide 42: a sleeping thread is woken by an exception
try { Thread.sleep(100000); }
catch (InterruptedException e) { b = false; }   // stop

Now you know what all those catch (InterruptedException e) {} blocks in the slides are about. An empty catch ignores a request to stop. That's harmless in short demo programs, but in slide 42 the catch is the only way the thread ever finishes.

"If this thread is blocked in an invocation of … join() … sleep(long) … then its interrupt status will be cleared and it will receive an InterruptedException." Thread.interrupt()

2 · Suspend and resume

Deck 4 · slides 43–46

TSuspendResume is a worker that another thread can pause and restart. Between pieces of work, the worker checks a suspended flag, and if it's set, it waits on a resume condition:

public void run() {
    while (go) {
        // do work
        lock.lock();
        try {
            while (suspended) resume.await();  // + try/catch
        } finally { lock.unlock(); }
    }
}
public void tSuspend() { suspended = true; }
public void tResume() {
    suspended = false;
    lock.lock();
    try { resume.signal(); } finally { lock.unlock(); }
}

The thread pauses itself at a safe point, between pieces of work and never halfway through one. suspended and go are volatile because they're written outside the lock (lesson 9). tResume takes the lock only because signal() requires it (lesson 12).

3 · A buffer that holds one value

Deck 4 · slides 47–50

Slide 47 asks for a buffer holding a single int. A reader waits until there's a value, takes it and clears the buffer. A writer waits until the buffer is clear. This is lesson 12's bounded buffer with max = 1, and a boolean item replaces the count:

public int read() {                 // slide 49
    lock.lock();
    try {
        while (!item) full.await();     // + try/catch
        item = false;
        empty.signal();
        return x;
    } finally { lock.unlock(); }
}
// write(k): while (item) empty.await();
//           x = k; item = true; full.signal();

Here the slides signal on every read and write, which is correct. Note that return x inside try still runs the finally before the method returns, so the lock is always released.

4 · The bag of sweets, and a bathroom

Deck 4 · slides 51–56

Slide 51 is just a title ("Pipeline Problem, Thread Topologies?") with nothing on it. Slide 52 sets the exercise below. Slides 53–56 are a bag of sweets: take() waits on notEmpty while bag == 0 and then takes one, and a Parent thread keeps calling put(). Two of lesson 12's warnings apply here:

  • put() signals only if (bag == 1), the "just stopped being empty" check. With several children waiting, it can leave one asleep while sweets are in the bag. Signal every time.
  • Parent's go flag isn't volatile, so setting it from another thread might never stop the loop (lesson 2).

The bathroom (slide 52). A bathroom is either empty, used by women only, or used by men only. Anyone may enter an empty bathroom. While women are inside, more women may enter but no men, and the other way round. Capacity is unlimited. One way to plan it, the same way as every problem in this deck:

  1. State: women and men inside now.
  2. When must enter(woman) wait? While someone of the other gender is inside.
  3. Who changes that, and whom must they wake? The last person of a gender to leave makes the room empty, and then everyone waiting may be able to enter.

Check yourself

Answer from memory, without scrolling up. You get one click per question.

Main calls t.interrupt() while t is inside Thread.sleep(100000). What happens?

A blocked thread is woken by the exception (slide 42), and its catch decides what to do. A running thread just has its interrupted status set and must check it (slide 41).

What's the risk in catch (InterruptedException e) {} inside a loop?

The exception is how the thread hears "please stop", and catching it also clears the interrupted status. An empty catch just carries on as if nothing had happened.

In suspend/resume, where does the worker actually pause?

tSuspend() only sets a flag. The worker notices it at its own safe point and waits on resume, so it never stops halfway through a piece of work.

In the bathroom, when the last woman leaves, why wake all waiting threads rather than one?

Capacity is unlimited, so once the room is empty, every waiting man is allowed in. It's the same reason stopWrite wakes all readers in lesson 13.

Stuck? Hint

enter(woman): inside the usual lock/try/finally, while (woman ? men > 0 : women > 0) await, then increment your own counter. leave(woman): decrement your counter, and if both counters are now 0, signalAll().

Stretch: break it on purpose

(a) Replace signalAll() with signal(). Does it still pass? Is it still a good solution? (b) A fairness question for the exam: can a steady stream of women keep a man out forever?

Solution (only after trying) 
void enter(boolean woman) {
    lock.lock();
    try {
        while (woman ? men > 0 : women > 0) {
            try { changed.await(); }
            catch (InterruptedException e) {}
        }
        if (woman) women++; else men++;
    } finally { lock.unlock(); }
}
void leave(boolean woman) {
    lock.lock();
    try {
        if (woman) women--; else men--;
        if (women == 0 && men == 0) changed.signalAll();
    } finally { lock.unlock(); }
}

(a) It still passed on my machine, because it's still safe. But it lets in only one waiting person each time the room empties, even though everyone waiting is allowed in. (b) Yes. As long as at least one woman is inside, more women can enter and the room never empties, so a man can starve. Fixing that needs a rule like lesson 13's "a waiting writer blocks new readers".

Exam practice

Describe two ways of terminating a thread from another thread, and when each one works. (4 marks)

(1) A volatile boolean flag that the thread checks in its loop (Deck 1 s72–74). It's simple, but a thread that is sleeping or waiting won't notice the flag until it wakes. (2) t.interrupt() (Deck 4 s40–42). A running thread must poll isInterrupted(), but a thread blocked in sleep, join or await is woken at once with an InterruptedException and can end in its catch. Either way the thread stops itself. Neither forcibly kills it.

Next time, from memory

What does interrupt() do to a running thread, and to a sleeping one?

Running: sets its interrupted status, which it must check with isInterrupted(). Sleeping, joining or awaiting: the call throws InterruptedException and the status is cleared.

Plan any condition-variable problem in three questions.

What's the state? When must each method wait? Who changes the state, and whom must they wake (one or all)?

Why does a volatile flag work for stopping a thread, but a plain boolean may not? (lesson 2)

Without volatile (or a lock), there's no guarantee the running thread ever sees the other thread's write. It may keep using its cached value forever.
