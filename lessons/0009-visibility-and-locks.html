Visibility and Locks

What a lock guarantees besides “one at a time”, which object each lock really is, and what a monitor is.

Your win today: you'll fix two lock bugs taken straight from the slides: a static counter that loses updates, and a thread that won't stop. About 20 minutes.

Deck 3 slides 30–49 jump between visibility, the egg timer, static methods, a stack and monitors. One question connects them: what exactly does a lock protect? Answering it in order explains each slide group.

1 · Visibility

Deck 3 · slides 30–32

Lesson 8 was about atomicity: nobody sees an update half-done. This is a second, separate problem. Without synchronization there is no guarantee that one thread ever sees another thread's write (slide 30). Compilers and CPUs may reorder instructions, and each core may keep its own cached copy of a variable. Slide 31: without synchronization, you can't reason about the order in which memory changes happen.

The lock fixes this too (slide 32). If T1 releases a lock and T2 then takes the same lock, T2 sees every change T1 made before releasing it.

Java's spec calls this a happens-before relationship: “An unlock on a monitor happens-before every subsequent lock on that monitor.” JLS §17.4.5. Oracle's tutorial page Memory Consistency Errors explains it in plain words.

2 · The egg timer again

Deck 3 · slides 33–36

Lesson 2 stopped a thread with private volatile boolean go. Slide 35 offers two solutions:

synchronized void terminate() { go = false; }  // (1)
private volatile boolean go = true;            // (2)

(1) alone does not work. The lock only gives visibility to a thread that takes the same lock, and run()'s while (go) takes no lock. I tested it on Java 26 with a busy loop: the thread never stopped, 3 runs out of 3. It works only if the loop also reads go through a synchronized method. Slide 34's loop sleeps for a second each time round, which usually hides the bug but doesn't fix it.

Slide 36 is the sentence to learn for the exam:

  • A lock gives atomicity and visibility.
  • volatile gives visibility only.

So volatile is right for a stop flag, which is a single write and a single read. It is wrong for a counter: with a volatile int, two threads doing count++ a million times each still reached only about 1.3 million in my test, because ++ is three steps (lesson 8).

3 · Static methods lock the class

Deck 3 · slides 37–43

A synchronized instance method locks this. A synchronized static method has no this, so it locks the class object, written Counter.class (slides 38–40). These are two different locks:

class Counter {
    private static int next = 0;
    // locks Counter.class
    synchronized static int getNext() {
        next++; return next;
    }
    // locks this: same data, other lock!
    synchronized void reset() { next = 0; }
}

That's slide 42's bug: getNext and reset can run at the same time and corrupt next (slide 41). Slide 43's fix is to make the instance method take the class lock:

void reset() {
    synchronized (this.getClass()) { next = 0; }
}
Counter.class is safer than this.getClass(): if reset were called on an object of a subclass, getClass() would return the subclass, which is yet another lock.

The rule: static data needs the class lock, every time.

4 · Reentrant locks

Deck 3 · slides 44–47

Slide 45's stack has synchronized push, which calls synchronized full on the same object. The thread already holds the lock when it calls full. Does it wait for itself forever? No. Java's locks are reentrant: a thread that holds a lock can enter other blocks guarded by the same lock (slide 44). This also lets you call several synchronized methods in a row inside one bigger synchronized block, without another thread getting in between.

5 · Monitors

Deck 3 · slides 48–49

The theory name for all this is a monitor (slide 48): data plus a lock that gives one thread at a time exclusive access, plus a queue of threads waiting to enter. A Java object with synchronized methods is a monitor. The name goes back to Brinch Hansen and Hoare in 1973, from lesson 3's history slide.

Check yourself

Answer from memory, without scrolling up. You get one click per question.

What does volatile give you that a plain field doesn't?

Slide 36: a lock gives atomicity and visibility; volatile only visibility. A volatile counter still loses updates under ++.

Which lock does a synchronized static method take?

There is no this in a static method, so Java locks the class object. Instance methods lock this, a different lock, which is slide 41's problem.

A thread inside synchronized push() calls synchronized full() on the same object. What happens?

A thread that already holds a lock can take it again (slide 44). Without reentrancy, any synchronized method calling another synchronized method would hang.

Only terminate() is synchronized; run() loops on a plain go. Is the thread guaranteed to stop?

Visibility comes from the reader and writer taking the same lock (slide 32). With only the writer locked, the reader may keep its cached true forever; in my test it did.

Exam practice

Distinguish atomicity and visibility, and state what synchronized and volatile each guarantee. (4 marks)

Atomicity: an action happens as one indivisible step, so no thread sees it half-done (e.g. a whole count++). Visibility: a value written by one thread is seen by other threads that read it later. Without synchronization neither is guaranteed, because of caching and reordering. synchronized (a common lock) gives both: mutual exclusion inside the block, and a thread taking a lock sees all changes made before the previous release of that lock. volatile gives visibility only: reads always see the latest write, but compound actions like ++ can still interleave.

Marks are my estimate, not taken from your exam.

Next time, from memory

Lock vs volatile, in one line.

A lock gives atomicity and visibility; volatile gives visibility only.

Which lock protects static data?

The class lock, ClassName.class, which is what synchronized static methods use. Instance methods must lock it explicitly.

Why must a check-then-act be inside one lock? (lesson 8)

Otherwise another thread can change the state between the check and the act, e.g. two withdrawals both passing the balance check.
