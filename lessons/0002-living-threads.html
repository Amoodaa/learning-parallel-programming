Living Threads

Pause a thread, see what state it's in, and stop it cleanly.

Your win today: you'll stop a thread that's spinning flat out, and see why adding one keyword is the difference between FAIL and PASS. About 20 minutes.

In lesson 1 a thread was started, did its job, and finished. Slides 49–89 of Deck 1 cover what happens while a thread is running. Slide 49 lists ten thread methods. Only three of them matter much: sleep, thread states, and stopping. The rest fit in one table.

1 · sleep()

Deck 1 · slides 50–56

try {
    Thread.sleep(500);   // pause for 500 ms (1000 ms = 1 s)
} catch (InterruptedException e) {
    return;              // woken early: usually means "stop"
}

Two facts that the slides leave out:

  • sleep always pauses the current thread, meaning whichever thread runs that line. It's a static method, so this.sleep(…) on slides 50, 67 and 73 is misleading: if main called t.sleep(1000), main would be the one that sleeps.
  • Why the try/catch? Another thread can interrupt a sleeping thread to wake it early, and sleep reports that by throwing InterruptedException. Java makes you handle it. Slide 53 handles it with return, which ends the thread.
“Thread.sleep causes the current thread to suspend execution for a specified period.” Oracle: Sleep. On interrupts: “It's up to the programmer to decide exactly how a thread responds to an interrupt, but it is very common for the thread to terminate.” Oracle: Interrupts

Slides 52–56: countUp sleeps 300 ms and countDown sleeps 500 ms, so their output interleaves at roughly a 5:3 ratio. The exact interleaving changes from run to run.

3 · Thread states

Deck 1 · slides 66–68

t.getState() returns one of six values. Here they are in the order a thread passes through them:

StateMeaning
NEWCreated, start() not called yet.
RUNNABLERunning, or ready to run as soon as the scheduler picks it.
TIMED_WAITINGPaused for a set time: sleep(ms), join(ms).
WAITINGPaused with no time limit, e.g. join().
BLOCKEDWaiting for a lock (covered in a later lecture).
TERMINATEDrun() has finished.
Slide 66 says TIME_WAITING; the real name is TIMED_WAITING. Thread.State Javadoc

Slide 68's program prints NEW, RUNNABLE, TIMED_WAITING, TERMINATED. I ran it to confirm. Try tracing it yourself in question 1 below.

4 · Stopping a thread

Deck 1 · slides 72–74, 86–88

A thread stops when its run() returns. To stop one from outside, give it a flag to check (slide 73, EggTimer):

class EggTimer extends Thread {
    private volatile boolean go = true;   // the key word
    public void run() {
        while (go) { /* work */ }
    }
    public void terminate() { go = false; }
}

Why volatile? Without it, the running thread is allowed to keep reading an old, cached value of go, so it might never see main's go = false. volatile guarantees that a write by one thread is visible to the others.

“Changes to a volatile variable are always visible to other threads.” Oracle: Atomic Access

Slides 86 and 88 (MessagePrinter, PrimeGenerator) use a stop flag without volatile. That's a bug, even if those programs happen to work: printing and sleeping inside the loop often hide it. A tight loop with no printing exposes it, and that's what your exercise does.

Check yourself

Answer from memory. You get one click per question.

Slide 68: t sleeps 4 s. Main starts it, sleeps 1 s, then prints t.getState(). What's printed?

After 1 s, t is still inside sleep(4000), which is a pause with a time limit. A thread that's only waiting for a lock would be BLOCKED, and one paused with no time limit would be WAITING.

main calls t.sleep(1000), where t is another running thread. What happens?

sleep is static and always pauses the current thread, which here is main. Writing it as t.sleep compiles but misleads, which is why Thread.sleep(…) is the clear way to write it.

Why is EggTimer's go flag declared volatile?

volatile is about visibility: one thread's write is guaranteed to reach another thread's read. It doesn't restrict who writes (that's locking, in a later lecture). If anything, it makes the loop slightly slower.

You call t.setPriority(Thread.MAX_PRIORITY). What does that guarantee?

Slide 69: “the underlying operating system can influence the order in which threads are executed.” Priority is a hint, never a guarantee.

Why do the slides wrap every sleep in try/catch?

An interrupt from another thread ends the sleep early and throws InterruptedException, which Java makes you catch or declare.

Stuck? Hint

TODO 2 is one assignment. TODO 1 is one keyword, and section 4 above tells you which.

Solution (only after trying) 
private volatile boolean running = true;
...
public void terminate() { running = false; }

Without volatile, the JIT compiler is allowed to read running once and turn the loop into while (true). The write from main happens, but the worker never looks again.

Which thread does x.sleep(100) pause?

The current thread, whoever runs that line. sleep is static, and the x. is ignored.

Name the six thread states in order.

NEW → RUNNABLE → BLOCKED / WAITING / TIMED_WAITING → TERMINATED.

How do you stop a thread from outside, and what does the flag need?

Have run() loop on a boolean flag and give the class a method that sets it to false. The flag must be volatile so the running thread sees the change.
