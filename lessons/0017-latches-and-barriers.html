Latches and Barriers

Two ready-made ways to make a group of threads wait. A latch waits for events to happen; a barrier waits for threads to arrive.

Your win today: you'll fix a one-thread-per-element array smoother that gives wrong answers in 100 trials out of 100. About 20 minutes.

Deck 6 (Latches and Barriers) moves from building tools yourself to using the ones in java.util.concurrent. You could build both of today's tools from lesson 12's conditions. Here they come ready-made. Slides 2–22 cover CountDownLatch and CyclicBarrier, and lesson 18 covers the rest of the deck.

1 · CountDownLatch: a gate

Deck 6 · slides 2–8

A latch is a gate (slide 2). It starts with a count of events. countDown() records one event, and await() blocks until the count reaches 0. Then the gate opens for good, and every waiting thread, and any thread that awaits later, passes straight through.

import java.util.concurrent.*;

CountDownLatch start = new CountDownLatch(1);
start.await();       // block until count is 0 (+ try)
start.countDown();   // count - 1; never blocks

The slides use it two ways:

  • Starting gun (slides 3–5): a latch of 1. Ten threads call start.await(), and main calls start.countDown() once to release them all together.
  • Finish line (slides 6–8): a second latch of 10. Each thread calls end.countDown() when it's done, and main calls end.await(). That's lesson 1's join() loop in one call, and it works even when you don't have the Thread objects.

A latch can't be reset. Once it's open, it stays open.

2 · CyclicBarrier: a meeting point

Deck 6 · slides 9–14

A barrier is lesson 15's rendezvous for a whole group (slide 9). You create it for n parties, and each thread that calls await() blocks until all n have called it. Then all are released together, and the barrier resets itself, ready for the next meeting. That's why it's called cyclic.

CyclicBarrier barrier = new CyclicBarrier(3);
try { barrier.await(); }                  // wait for all 3
catch (InterruptedException e) {}
catch (BrokenBarrierException e) {}       // someone gave up

BrokenBarrierException is thrown if another party is interrupted or times out while waiting. The barrier is then "broken", so the remaining threads don't wait forever.

Slides 10–14 use both tools. Three threads share one array. Each first fills its own third with random numbers (using lesson 4's j*N/k split), then calculates something over the whole array: the sum of the odd numbers, the sum of the even numbers, or how many odd numbers there are. No thread may start calculating until all three thirds are filled, so each calls barrier.await() between the two phases. main waits for all three with a latch of 3.

3 · The barrier action

Deck 6 · slides 15–17

new CyclicBarrier(n, action) takes a Runnable that runs once each time the barrier trips. It runs after the last thread arrives and before any is released (slide 15), so it's the place to check or update shared state between phases. Slide 16 describes an example: 5 threads fill their own segments, and the barrier action checks the whole array before they continue. Slide 17, which would have shown the code, is blank.

4 · The array smoother

Deck 6 · slides 18–22

Replace each element with the average of itself and its neighbours (slide 18), using one thread per element. Each thread must read the old values of its neighbours, but the neighbours are writing new values into the same array. The fix is a barrier between reading and writing:

double sum = data[k];                      // read phase
if (k > 0) sum += data[k - 1];
if (k < data.length - 1) sum += data[k + 1];
barrier.await();                           // all have read
data[k] = sum / 3.0;                       // write phase
latch.countDown();                         // tell main

Without the barrier, thread 5 might read data[4] after thread 4 has overwritten it. That's a race (lesson 3), and the result depends on timing.

Two notes on slides 18–22. The end elements have only one neighbour, but slide 22 still divides by 3, so data[0] becomes (2 values)/3. Divide by the number of values actually added. Also, one thread per element is fine for 10 elements, but Deck 2 slides 15–21 (lesson 4) showed it's slower than no threads at all for 100,000.

Check yourself

Answer from memory, without scrolling up. You get one click per question.

Ten threads must all start at the same moment when main says go. What do you use?

One event ("go") is enough, and many threads wait for it. A latch of 10 that main awaits is the other pattern: waiting for all threads to finish.

What's the main difference between a latch and a barrier?

A latch counts events and opens for good. A barrier makes its own parties wait for each other, then resets for the next round (slide 9).

In the smoother, what goes wrong without the barrier?

Each thread writes only its own element, but reads its neighbours'. The barrier makes sure every read finishes before any write starts.

When does a CyclicBarrier's barrier action run?

That's why it's useful for checking or updating shared state between phases (slide 15): nobody is running at that moment.

Stuck? Hint

Both are created with n: the barrier needs all n threads to arrive, and the latch counts n finishes. Put barrier.await() between the reads and the write (it needs a try with two catches), done.countDown() after the write, and done.await() at the end of smooth().

Stretch: break it on purpose

(a) Remove only the barrier. (b) Put it back and remove only done.await(). Each mistake alone, how many trials are wrong? (c) Could join() replace the latch here?

Solution (only after trying) 
CyclicBarrier barrier = new CyclicBarrier(n);
CountDownLatch done = new CountDownLatch(n);
// in each thread, after the reads:
try { barrier.await(); }
catch (InterruptedException
       | BrokenBarrierException e) {}
data[k] = sum / count;
done.countDown();
// after the loop:
try { done.await(); } catch (InterruptedException e) {}

(a) and (b): 100 of 100 wrong each time on my machine. Each one alone is enough to break it. (c) Yes, if you keep the 40 Thread objects in an array and join them all. The latch just saves you keeping them, which matters when the work runs in a pool (lesson 18).

catch (A | B e) is Java's multi-catch: one block for either exception.

Exam practice

Compare CountDownLatch and CyclicBarrier, with a use for each. (4 marks)

A CountDownLatch is initialised with a count. Threads calling await() block until countDown() has been called that many times, and then the latch stays open forever: it is one-use. Use: main waits for n worker threads to finish, or n threads wait for one start signal. A CyclicBarrier is initialised with a number of parties. Each party's await() blocks until all have arrived, then all are released and the barrier resets for reuse. It can also run an optional barrier action. Use: threads that must all finish one phase, such as initialising an array, before any starts the next.

Marks are my estimate, not taken from your exam.

Why is a barrier "cyclic"?

After all parties arrive and are released, it resets, so the same barrier can be used again for the next phase.

What's a binary semaphore, and what is it equivalent to? (lesson 15)

A semaphore that starts at 1. Acquire and release around a critical section make it work as a lock.
