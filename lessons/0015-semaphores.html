Semaphores

A counter of permits. Depending on where it starts, the same tool is a lock, a "go" signal, or a limit on how many threads get in.

Your win today: you'll make one thread wait for another, make two threads meet, and cap a tunnel at 3 cars, all with semaphores. About 20 minutes.

Deck 5 (Semaphores) gives a second tool for what Deck 4 did with conditions. Deck 1 slide 32 mentioned Dijkstra's semaphore from 1965, and this is it. Slides 2–23 introduce it through four patterns, and the last one rebuilds lesson 12's producer/consumer. Lesson 16 covers the puzzles in slides 24–45.

1 · What a semaphore is

Deck 5 · slides 2–5

A semaphore holds a count of permits and has two operations (slides 2–3):

  • acquire(): if the count is above 0, take one and carry on. If it's 0, sleep until one is released. The check, the decrement and going to sleep are one atomic step.
  • release(): add one permit. If threads are sleeping in acquire(), one of them gets it and carries on.
import java.util.concurrent.*;

Semaphore sem = new Semaphore(1);   // starting permits
try { sem.acquire(); }              // may throw
catch (InterruptedException e) {}
// ...
sem.release();

A semaphore that starts at 1 is a binary semaphore, which works as a lock: slides 4–5 protect x = x + 1 with one. There's one difference from a lock: a permit has no owner. Any thread may release, even one that never acquired. The next two patterns rely on that.

"There is no requirement that a thread that releases a permit must have acquired that permit by calling acquire()." Semaphore Javadoc

2 · Signalling: "go first", and meeting up

Deck 5 · slides 6–13

Order (slides 6–9). TA must run before TB, whichever starts first. Use a semaphore that starts at 0, so the permit is a message saying "TA is done":

Semaphore sem = new Semaphore(0);
// TA:  work;  sem.release();
// TB:  sem.acquire();  work;   // blocks until TA's release

Rendezvous (slides 10–13). Each thread must reach a point before the other goes past it: TA's st2 waits for TB's st3, and TB's st4 waits for TA's st1. Use two semaphores, both starting at 0, one for each "I've arrived" message:

// TA: st1; aArrived.release(); bArrived.acquire(); st2;
// TB: st3; bArrived.release(); aArrived.acquire(); st4;

Each thread releases its own message before waiting for the other's. If both waited first, each would wait for a release that never comes: a deadlock. (Slide 11's comment, copied from slide 7, says "TA executes before TB". That's wrong here: in a rendezvous neither goes first.)

3 · Counting: the tunnel

Deck 5 · slides 14–19

At most n cars may be in a tunnel at once (slide 14). Start the semaphore at n: each car acquires a permit to enter and releases it when it leaves, so car n + 1 waits (slides 15–17). Slide 18 adds a point that's easy to miss: the semaphore allows n threads in at once, so it does not protect data. The count of cars inside is updated by several threads at once, so it needs its own protection: an AtomicInteger (lesson 19), or a lock.

Don't acquire() inside synchronized (slide 19). In slide 19, t() is synchronized and blocks in sem.acquire(). The only thread that can release is in t1(), which is also synchronized on the same object. So t() holds the lock while waiting for a permit, and t1() waits for the lock before it can release one. That's a deadlock. Unlike await() (lesson 12), acquire() does not release any lock you hold.

4 · Producer/consumer with semaphores

Deck 5 · slides 20–23

Lesson 12's bounded buffer again, with two semaphores instead of two conditions. Both count something:

Slide's nameWhat it countsStarts atacquire()release()
fullfree slotsmaxproducer, before addingconsumer, after removing
emptyitems in the buffer0consumer, before removingproducer, after adding

The names are confusing: empty counts items, and the consumer waits on it when the buffer is empty. Read them as "the semaphore that controls the consumer" and "the one that controls the producer", which is how slide 20 describes them.

public void put(E x) {           // slide 22
    full.acquire();        // wait for a free slot (+ try)
    lock.lock();
    try {
        buffer.add(x);
        empty.release();         // one more item
    } finally { lock.unlock(); }
}

Two details. The semaphores only count, so a lock is still needed: two producers may both hold a permit and call add on the same ArrayList at once. And acquire() comes before lock(). The other way round, a producer would wait for a slot while holding the lock that consumers need to free one, which is slide 19's deadlock again.

Check yourself

Answer from memory, without scrolling up. You get one click per question.

To make TB wait until TA has finished, what should the semaphore start at?

With 0 permits, TB's acquire() blocks until TA's release() creates one. Starting at 1 would let TB straight through.

In the rendezvous, why must each thread release() its own semaphore before it acquire()s the other?

Each would be waiting for a message the other hasn't sent yet, and neither can send it while waiting. That's a deadlock.

The tunnel semaphore starts at n. Why does the car count still need an AtomicInteger?

A semaphore with n permits lets n threads in together, so it gives no mutual exclusion among them. num++ from several cars at once would lose updates (lesson 8).

Slide 19: synchronized t() calls sem.acquire(), and synchronized t1() calls sem.release(). Why can this deadlock?

acquire() doesn't release locks you already hold. The thread that would release the permit is blocked waiting for that lock.

Exam practice

Define a semaphore and its two operations. Show how a semaphore can make thread TA execute before thread TB. (5 marks)

A semaphore is a non-negative counter with two atomic operations. acquire() decrements it if it's above 0, and otherwise blocks until it can. release() increments it, letting one blocked thread complete its acquire(). To order TA before TB: create new Semaphore(0) and share it. TA does its work and then calls release(). TB calls acquire() first, which blocks until TA's release, and then does its work. Whichever thread is scheduled first, TB's work cannot start before TA's release.

Explain how two semaphores and a lock implement a bounded buffer. (5 marks)

One semaphore counts free slots and starts at max. The other counts items and starts at 0. The producer acquires a free slot, adds the item under the lock, then releases an item permit. The consumer acquires an item permit, removes the item under the lock, then releases a free slot. The producer therefore blocks when the buffer is full and the consumer when it's empty. The lock is still needed because several threads holding permits may change the list at once. The semaphore is acquired before taking the lock, so no thread blocks while holding it.

What starting value gives (a) a lock, (b) "wait for my signal", (c) "at most n at once"?

(a) 1. (b) 0. (c) n.

Name one way a semaphore differs from a ReentrantLock.

Any thread may release a permit; nobody owns it. A lock must be unlocked by the thread that locked it. (A semaphore also isn't reentrant, and can allow n threads at once.)

Why does await() release the lock, and why does that matter? (lesson 12)

So that another thread can take the lock and change the condition. Otherwise the waiter would block everyone, as acquire() inside synchronized does on slide 19.
