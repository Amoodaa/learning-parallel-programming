Condition Variables

A lock lets one thread in at a time. A condition variable lets a thread wait inside the lock until something is true, such as "the buffer isn't full".

Your win today: you'll write a bounded buffer that 4 producers and 4 consumers share without losing an item or hanging. About 25 minutes.

Deck 4 (Condition Variables) starts where Deck 3 stopped. Lessons 8–11 made threads take turns. Now a thread sometimes can't go ahead even when it has the lock: the garden is full, or the buffer is empty. Slides 2–16 show the tool for that and use it three times. The rest of the deck (lessons 13–14) applies it to classic problems.

1 · Sharing a limited resource

Deck 4 · slides 2–4

Slide 2 sums up the course so far: one lock can share one resource, and several locks can share several. The new question: how do you share a resource that is only available under some condition? Slide 3 gives real examples: a stadium, a restaurant or a bus has a fixed number of places. Slide 4 lists the problems the deck solves, the producer/consumer buffer, dining philosophers and readers/writers.

The difficulty: suppose the garden is full. The visitor thread has to wait, but it holds the lock, so nobody can leave and make room. It has to give the lock up while it waits, and take it back afterwards.

2 · await and signal

Deck 4 · slides 5–6

A condition variable belongs to a Lock (lesson 11). You can make several for one lock, one per thing you might wait for:

Condition notFull = lock.newCondition();

notFull.await();      // release the lock and sleep
notFull.signal();     // wake one thread waiting here
notFull.signalAll();  // wake all of them
  • await() releases the lock and puts the thread to sleep in one step. When the thread is woken it has to take the lock back before await() returns, so it still holds the lock afterwards.
  • signal() wakes one waiting thread, if there is one. If none is waiting, the signal does nothing and is not saved for later.
  • You must hold the lock to call await or signal. Otherwise Java throws IllegalMonitorStateException.

Slide 6's rule: always call await in a while loop, never an if. Between being woken and getting the lock back, another thread can get in first and use up the space. So when you get the lock back, the condition may be false again:

while (count == max) {      // re-check after every wake-up
    try { notFull.await(); }
    catch (InterruptedException e) {}
}
count++;                    // now count < max for sure
A second reason the slides don't give: the Condition Javadoc allows a "spurious wakeup", where a thread returns from await() without any signal. The while loop covers that too. Condition

3 · A garden and a set of ports

Deck 4 · slides 7–12

Slides 7–9 return to Deck 3's garden (slides 98–101), now with at most max visitors. T1() is one turnstile: lock, wait on notFull while count == max, then count++. leave() does count-- and signals notFull. Slide 9 is the visitor thread: it enters through a random turnstile, sleeps, then leaves. (Slide 9 is missing () after garden.T1, and T2 is never shown. It is the same as T1.)

Slides 10–12 manage 10 network ports with the same pattern. getPort() waits while available == 0, then finds a free port, marks it used and returns its number. freePort(k) marks it free, does available++ and signals. Every lesson in this deck repeats this shape:

lock.lock();
try {
    while (!canGo) cond.await();  // wait for the condition
    // change the state
    other.signal();               // tell whoever waits on it
} finally { lock.unlock(); }

4 · Producer/consumer

Deck 4 · slides 13–16

Slide 13 states the classic problem. A producer puts items into a fixed-size buffer and a consumer takes them out. If the buffer is full the producer sleeps until there's space, and if it's empty the consumer sleeps until there's an item. That keeps a fast producer from getting ahead of a slow consumer.

Slides 14–16 use two conditions on one lock: producers wait on notFull and consumers wait on notEmpty. put waits while size == max, adds the item, and signals notEmpty. get waits while size == 0, removes the oldest item, and signals notFull. Each method wakes the threads waiting on the other side.

Slide bug. Slide 15 signals only when the buffer has just stopped being empty: if(size - 1 == 0) notEmpty.signal();. Slide 16 has the same check for full. That works for one producer and one consumer. With more, a thread can be left asleep even though the buffer has an item for it:

  1. Consumers C1 and C2 both wait on an empty buffer.
  2. A producer puts an item. Size goes 0 → 1, so it signals, and C1 wakes up. C1 still has to get the lock back.
  3. Before C1 gets the lock, a producer puts again. Size goes 1 → 2, which isn't the "was empty" case, so there's no signal.
  4. C1 takes one item. One item is left, but C2 is still asleep and nothing will wake it.

With 4 producers and 4 consumers, the slides' version hung in 20 runs out of 20 on my machine. The fix: signal on every put and every get. A signal with no thread waiting costs almost nothing.

Check yourself

Answer from memory, without scrolling up. You get one click per question.

What happens to the lock when a thread calls cond.await()?

Releasing the lock is the point: otherwise no thread could change the condition. And because await() takes the lock back before returning, the code after it is still inside the lock.

Why while (size == max) notFull.await(); rather than if?

Another thread can take the space between the signal and your re-locking (slide 6). Spurious wakeups are a second reason. Re-check every time.

In the bounded buffer, which condition should get() signal after removing an item?

Removing an item makes space, and producers are the ones waiting for space, on notFull. Each side signals the condition the other side waits on.

Nobody is waiting on notEmpty and a producer calls notEmpty.signal(). What happens?

A signal only wakes threads that are already waiting. That's why the waiting side checks the state (size == 0) instead of relying on having heard a signal, and why signalling every time is cheap.

Stuck? Hint

Use the shape from section 3. In put: lock.lock(), then try, then while (items.size() == max) await notFull, then items.add(x) and notEmpty.signal(), then finally { lock.unlock(); }. get is the mirror image: items.remove(0) returns the oldest item.

Stretch: break it on purpose

(a) Change put to signal only when the buffer was empty, as slide 15 does (if (items.size() == 1)). Run it a few times. (b) Change a while to an if. Does the checker catch it?

Solution (only after trying) 
void put(E x) {
    lock.lock();
    try {
        while (items.size() == max) {
            try { notFull.await(); }
            catch (InterruptedException e) {}
        }
        items.add(x);
        notEmpty.signal();
    } finally { lock.unlock(); }
}

E get() {
    lock.lock();
    try {
        while (items.isEmpty()) {
            try { notEmpty.await(); }
            catch (InterruptedException e) {}
        }
        E x = items.remove(0);
        notFull.signal();
        return x;
    } finally { lock.unlock(); }
}

(a) It hangs, and the checker reports "still running after 10 s". (b) It fails at once. In my runs, consumers crashed with IndexOutOfBoundsException because they woke up, didn't re-check, and removed from an empty list. Producers overfilled the buffer the same way. That is slide 6's scenario: another thread got the lock first and used up what the signal was for.

Exam practice

Explain why a call to await() on a condition variable must be enclosed in a while loop. (3 marks)

A signalled thread does not continue immediately. It must first reacquire the lock, and it may lose that race to another thread (slide 6). That thread can change the state, for example by filling the space that was freed, so the condition that caused the signal may no longer hold. The waiting thread must therefore test the condition again after every wake-up and wait again if it is false. A while loop does this. It also handles spurious wakeups.

Describe the producer/consumer problem and how two condition variables solve it. (5 marks)

A producer and a consumer share a fixed-size buffer. The producer must not add to a full buffer, and the consumer must not take from an empty one. Each must sleep until the other changes the state (slide 13). Solution: one lock protects the buffer, with two conditions on it. put waits on notFull while the buffer is full, adds, then signals notEmpty. get waits on notEmpty while it is empty, removes, then signals notFull. Waiting releases the lock, so the other side can make progress. The waits are in while loops, and the buffer updates happen under the lock, so they are atomic.

Why can signalling only on the "was empty" step hang a buffer with several consumers?

Two puts can happen before the first woken consumer gets the lock back. Only the first put signals, so a second waiting consumer sleeps while an item is in the buffer.

What does tryLock() do, and which deadlock condition does it break? (lesson 11)

It takes the lock if it's free and returns false immediately if not. A thread never waits while holding a lock, so it breaks hold and wait.
