Thread Pools

Stop making threads yourself: hand tasks to a pool and collect the results.

Your win today: you'll rewrite lesson 4's sum so a pool runs it, using Callable and Future, and see it print PASS. About 25 minutes.

Deck 2 slides 43–72 introduce a lot of new Java names at once. Each one replaces something you already know from lessons 1 and 4, and the table in section 4 lines them up. Slides 67–72 then redo lesson 4's sum with them.

1 · Why a pool

Deck 2 · slides 43–46

Lesson 4 showed that threads cost something to create. A thread pool creates a fixed number of threads once and reuses them. Work is handed over as tasks, which wait in a shared queue (slide 44). Each pool thread repeats the same loop (slide 45):

  1. Take the next task from the queue, waiting if it's empty.
  2. Run it.
  3. Go back for another.

This separates what to do (the tasks) from who does it (the pool's threads). Servers use pools so they don't create a new thread for every request (slide 46).

Oracle: “Using worker threads minimizes the overhead due to thread creation.” A fixed pool also degrades gracefully: under heavy load it slows down instead of collapsing under thousands of threads. Thread Pools

2 · Create, submit, shut down

Deck 2 · slides 47–49, 52–60

import java.util.concurrent.*;   // all the pool classes

ExecutorService pool =
    Executors.newFixedThreadPool(k);  // k threads
pool.submit(task);   // queue a task; returns at once
pool.shutdown();     // accept no more; finish the queue

ExecutorService is the pool's type, and Executors (with an s) is the class whose static methods make pools. submit doesn't run the task in main; it puts it in the queue and returns immediately, just as start() returns immediately.

Always call shutdown(). The pool's threads keep waiting for more tasks, and the JVM doesn't exit while they're alive. Forget it and your program prints its answer and then hangs (I checked this on Java 26). shutdown() doesn't wait for anything; it lets the queued tasks finish and then lets the threads end.

To wait for everything, slide 58 calls shutdown() and then awaitTermination(1000L, TimeUnit.SECONDS), which blocks until all tasks have finished or the timeout passes (slide 49). Slide 54 waits a different way: through the tasks' Futures (section 4).

Javadoc for shutdown(): “previously submitted tasks are executed, but no new tasks will be accepted … This method does not wait for previously submitted tasks to complete execution. Use awaitTermination to do that.” ExecutorService

3 · Runnable or Callable

Deck 2 · slides 51, 55, 61–64

A task is one of two kinds (slide 51):

  • Runnable: void run(). Returns nothing. This is the same interface as lesson 1's Way B. Slides 55 and 60 are Runnables.
  • Callable<V>: V call(). Returns a value of type V, and may throw an exception (slides 61–62).
class Square implements Callable<Integer> {
    private int n;
    Square(int k) { n = k; }
    public Integer call() { return n * n; }
}

Syntax: <Integer> is a generic type argument. It fills in V, so this task's call() returns an Integer. Generics only accept object types, so you write Integer, not int. Java converts between the two automatically, which is why return n * n; compiles (this is called autoboxing).

4 · Future: the result, later

Deck 2 · slides 50, 53–54, 65–66

submit returns a Future, a receipt for a result that may not exist yet. future.get() waits until the task has finished, then returns what call() returned (slide 50):

Future<Integer> f = pool.submit(new Square(6));
int r = f.get();   // waits, like join(); r = 36

get() can throw two checked exceptions. InterruptedException is the same as join()'s. ExecutionException wraps any exception that call() threw in the pool thread, so the error reaches main. The slides catch both and do nothing, which hides errors; writing throws Exception on main is simpler and shows them.

5 · Sum with a pool

Deck 2 · slides 67–72

Slides 67–72 are lesson 4's fair split rewritten with these replacements. Slide 68 is the same j*N/k formula. Slide 69 submits one Sum per segment and keeps every Future in an ArrayList. Slide 70 calls get() on each one. It's the same shape as lesson 1: submit all, then get all.

Calling get() right after each submit(), inside the same loop, makes the program serial: main waits for task 0 before submitting task 1. This is the same mistake as start(); join(); in one loop.

Check yourself

Answer from memory, without scrolling up. You get one click per question.

You want each task to send back a number. Which interface do you implement?

Callable's call() returns a value. Runnable's run() is void. A Future is what you get back from submit, and ExecutorService is the pool itself.

A program submits its tasks, prints every result, but never calls shutdown(). What happens?

The pool's threads stay alive, waiting for more tasks, and the JVM waits for them. Everything runs and prints correctly; the program just never ends.

What does future.get() do if the task hasn't finished yet?

Slide 50: get waits if necessary for the computation to complete, then retrieves its result. That's why it replaces both join() and getResult().

A pool of 2 threads gets 4 submitted tasks (slides 52–55). How many threads does it create?

A fixed pool has exactly the number of threads you asked for. Tasks 3 and 4 wait in the queue until a thread finishes its first task and comes back for another.

A task's call() divides by zero. Where does main see the error?

get() throws an ExecutionException whose cause is the ArithmeticException (checked on Java 26). With the slides' empty catch blocks, it would be silently lost.
