Blocking Queues and Pools Revisited

Lesson 12's bounded buffer, ready-made as ArrayBlockingQueue. Then Deck 6 goes back over thread pools, with two new details.

Your win today: you'll make two consumer threads stop cleanly when a producer runs out of work, using "sentinel" values. About 20 minutes.

Deck 6 slides 23–53 have two parts. Slides 23–32 replace the producer/consumer buffer you wrote by hand in lesson 12 with a library class. Slides 33–53 repeat Deck 2's thread pools (lesson 5) almost slide for slide. This lesson spends its time on the queue and only points out what's new in the pool slides.

1 · ArrayBlockingQueue

Deck 6 · slides 23–24

A first-in-first-out queue with a fixed capacity, held in an array (slide 23): exactly lesson 12's bounded buffer. Its two blocking methods (slide 24):

ArrayBlockingQueue<Job> q = new ArrayBlockingQueue<>(8);
q.put(job);        // waits while full
Job j = q.take();  // waits while empty; removes the head
// both may throw InterruptedException

Inside, it's the same lock and two conditions you wrote yourself, so you don't need to write them again. You can't change the capacity after creating it.

2 · Filling a matrix: one producer, two consumers

Deck 6 · slides 25–32

The job is to fill a 100×10 matrix one column at a time, with two consumers working in parallel on a dual-core machine (slide 26). Slide 25 says it's another version of a Deck 2 program.

  • BufferData (slide 27) is a job: a reference to the matrix plus a column number. The queue holds jobs, not numbers.
  • The producer (slide 30) puts one job per column, then two sentinels: jobs with null data and column −1.
  • Each consumer (slides 31–32) takes a job, fills its column, and repeats until it takes a sentinel. Then it stops.
  • main (slides 28–29) joins both consumers and prints the matrix.

Why sentinels? A consumer blocked in take() on an empty queue can't tell "no job yet" from "no job ever". A sentinel is a message in the queue itself that says "stop". It has to be one per consumer, because each consumer that takes one stops and doesn't pass it on. With only one sentinel, the other consumer waits in take() forever, and main's join() waits for it forever too.

The queue holds only 8 jobs, so the producer blocks in put() when it gets ahead. That's the point of a bounded buffer: the producer can't run away from slow consumers (lesson 12's slide 13).

3 · Thread pools, again

Deck 6 · slides 33–53

Most of this is lesson 5. Executors.newFixedThreadPool(k), submit, Future.get(), shutdown() and awaitTermination work as they did there. Slides 33–34 describe the pool's insides in words, and with this deck you can now read it as "worker threads consuming tasks from a blocking queue": each worker repeatedly takes the next task, runs it, and goes back to waiting. That reuse is why servers use pools: they avoid creating a thread per client request.

What's new compared with lesson 5:

  • A semaphore as the screen lock (slides 43–47). Four tasks each print a line of numbers, and the lines get mixed up. Each task now does screen.acquire(), prints its line, then screen.release(), with new Semaphore(1) shared between them. That's lesson 15's binary semaphore used as a lock (compare Deck 3's synchronized screen in lesson 8).
  • Reusing the pool (slide 45): after waiting for the first four tasks, main submits four more to the same pool. Creating a pool once and reusing it is the whole point.
  • Waiting two ways: slide 41 calls get() on every Future, and slide 46 calls shutdown() and then awaitTermination(1000, MILLISECONDS). That second call gives up after 1 s, and its boolean result (did everything finish?) is ignored.
Slide 36 says shutdown() will "shutdown pool when all submitted tasks complete". It doesn't wait: it stops new tasks being accepted and returns at once, while queued tasks keep running. Waiting is awaitTermination's job, which is why slide 46 calls both (lesson 5 has the Javadoc quote).

Slides 48–53 redo Callable: a Square task returns n*n, and main collects the Future<Integer>s in a list and calls get() on each. That's lesson 5's section 3. (Slide 49 writes E call(), but the interface's type parameter is V, as on slide 48.)

Check yourself

Answer from memory, without scrolling up. You get one click per question.

A producer calls put() on a full ArrayBlockingQueue. What happens?

put blocks while the queue is full and take blocks while it's empty (slide 24). It's lesson 12's notFull/notEmpty, built in.

There are two consumers. Why does the producer put two sentinels?

A consumer that takes the only sentinel stops. The other then blocks in take() forever, and main's join() hangs with it.

What does pool.shutdown() do?

Slide 36 implies it waits, but it doesn't. Follow it with awaitTermination (slide 46) or get() on every Future (slide 41) to wait.

Which one returns a value to the code that submitted it? (lesson 5)

call() returns a value and may throw a checked exception. run() is void. submit returns a Future either way, but a Runnable's future only tells you when it's done.

Stretch: break it on purpose

(a) Put only one sentinel. What does the checker report? (b) Without changing the producer, how could a consumer that takes the sentinel make sure the other consumer stops too?

Solution (only after trying) 
static void producer() throws InterruptedException {
    for (int c = 0; c < COLS; c++) queue.put(new Job(c));
    for (int i = 0; i < CONSUMERS; i++)
        queue.put(new Job(-1));
}

static void consumer() throws InterruptedException {
    Job job = queue.take();
    while (job.col() != -1) {
        fill(job.col());
        job = queue.take();
    }
}

(a) "still running after 5 s: a consumer is blocked in take()". (b) Put the sentinel back before stopping: queue.put(job); after the loop. Then the next consumer finds it too, and one sentinel is enough for any number of consumers. (This checker will still say FAIL, because it expects an empty queue and one sentinel is left at the end. The columns are all filled correctly.)

Exam practice

Describe the life cycle of a worker thread in a thread pool, and why pools are used in servers. (4 marks)

A pool has a fixed number of worker threads and a shared queue of tasks (Runnables or Callables). Each worker repeatedly takes the next task from the queue, waiting if it's empty, runs it to completion, and goes back for another (slides 33–34). The threads are created once and reused. Servers use pools because creating a new thread for every client request is expensive, and an unbounded number of threads would overload the machine. A pool caps the number of threads and avoids the creation cost.

How do the consumers in slides 30–32 know when to stop, and why is a special value needed? (3 marks)

After the real jobs, the producer puts one sentinel job per consumer (null data, column −1). A consumer loops on take() until it receives a sentinel, then exits. A special value is needed because take() on an empty queue just blocks: an empty queue can't tell a consumer that no more work is coming.

How many sentinels for k consumers, and why?

k. Each consumer stops at the first sentinel it takes and doesn't pass it on. (Or use one sentinel that each consumer puts back before stopping.)

What does shutdown() not do, and what does?

It doesn't wait. awaitTermination(timeout, unit) waits, and so does calling get() on every Future.

Latch or barrier: main waits for 3 workers to finish. (lesson 17)

A CountDownLatch(3): each worker calls countDown() and main calls await().
