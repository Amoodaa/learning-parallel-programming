Fair Splitting

How many threads to use, and how to give each one the same amount of work.

Your win today: you'll write the one-line formula that splits any array over one thread per core, and run lesson 1's sum on all your cores. About 25 minutes.

Deck 2 slides 2–41 look like five unrelated programs. They are one argument: each program shows a problem with the previous approach, and slide 24's formula fixes the last of them.

1 · It really is faster

Deck 2 · slides 2–13

Slides 2–4 are lesson 1's pattern applied to a search. Slide 5 admits it's too small: with 100 elements, creating the threads costs more than the search. That sentence comes back at slide 21.

Slides 8–12 do something big enough to be worth it. Two threads each selection-sort one half of a million numbers, then main merges the halves. Slide 13 reports about 4× faster on 2 cores.

Why 4× and not 2×? Selection sort takes about n² steps. Two halves take 2·(n/2)² = n²/2, so splitting alone halves the work, and running the halves at the same time halves it again. This explanation is mine; the slides give only the number.

2 · Too many threads is slower

Deck 2 · slides 14–21

If 2 threads help, why not one thread per element? Slides 15–20 try it with rank sort. An element's rank is how many elements are smaller than it, and that is its position in the sorted array:

int rank = 0;
for (int j = 0; j < data.length; j++)
    if (data[j] < data[i]) rank++;
copy[rank] = data[i];   // assumes no duplicates

Every element's rank can be computed independently, so slide 19 starts a RankerNoDup thread for each of the 100,000 elements. Slide 21: 75.4 s, against 72.5 s with no threads at all. The parallel version lost.

Slide 14 gives the rule this example teaches:

  • A CPU-bound program can't run more threads at once than there are processors. Extra threads only wait their turn, and each one still costs time to create and schedule.
  • So for CPU-bound work, use as many threads as processors, and share the work as fairly as possible between them.
  • I/O-bound work is different: those threads spend most of their time waiting, so more threads than cores can help (lesson 3's CPU- vs I/O-bound).

Java tells you the number of processors:

int k = Runtime.getRuntime().availableProcessors();
Javadoc: “Returns the number of processors available to the Java virtual machine.” java.lang.Runtime. Runtime.getRuntime() is just how you get the one Runtime object.

3 · The fair-split formula

Deck 2 · slides 22–27

Now split N items over k threads so no two pieces differ in size by more than 1 (slide 22). The obvious way fails. With N = 103 and k = 4, a base size of N/k = 25 leaves 3 items over, and if the last thread takes them the pieces are 25, 25, 25, 28 (slide 23).

Slide 24's fix is to compute k+1 boundaries instead of a size:

int[] index = new int[k + 1];
for (int j = 0; j <= k; j++)
    index[j] = (j * N) / k;
// thread j gets [index[j], index[j+1])

For N = 103, k = 4 this gives 0, 25, 51, 77, 103, so the pieces are 25, 26, 26, 26. Integer division rounds each boundary down, and that spreads the leftover items one at a time across the pieces. The first boundary is always 0 and the last is always N, so nothing is skipped.

j * N overflows int when N is large. With N = Integer.MAX_VALUE (the happy-numbers range) and k = 8, the boundaries come out as 0 268435455 0 …. Write (int) ((long) j * N / k) instead: casting j to long makes the multiplication happen in 64 bits.

Slide 26 plugs it into rank sort, with one RankerNoDup per processor, each looping over its own segment. (The constructor on slide 26 doesn't match slide 18; see the errata.) The result on slide 27: about 2× on 2 cores and about 8× on 8.

4 · Same recipe, bigger job

Deck 2 · slides 28–41

Happy numbers (slides 28–37) is not a new idea, just a CPU-heavy job to practise the split on: test every number up to Integer.MAX_VALUE. For the parallel part, isHappy(n) is simply “some work per number”. One HappyNumFinder per processor takes it from 420 s to 159 s (slides 38, 41).

Slide 39 splits with base = MAX / numProc, the slide 23 approach, and it never gives the leftover numbers to anyone, so up to numProc − 1 numbers at the end are never tested. The formula from slide 24 doesn't have this problem.

Check yourself

Answer from memory, without scrolling up. You get one click per question.

Use slide 24's formula with N = 10 and k = 4. What are the boundaries?

j·10/4 rounded down: 0, 2 (2.5), 5, 7 (7.5), 10. The pieces are 2, 3, 2, 3, so none differs by more than 1. 0, 2, 4, 6, 10 is the base-size approach, with the leftovers all dumped on the last thread.

Rank sort with one thread per element was slower than no threads. Why?

Only as many threads as processors can run at once. The other 99,998 add creation and scheduling cost without adding speed. The algorithm itself parallelises fine: slide 27 gets 8× with the same ranking code.

A CPU-bound job on an 8-core machine. How many threads should do the work?

Slide 14: use the maximum number of processors, but more threads than processors is counter-productive for CPU-bound work. More would only help if the threads spent time waiting on I/O.

Slide 39 uses base = MAX / numProc with segments [j·base, (j+1)·base). What goes wrong?

The last segment ends at numProc·base, which is less than MAX whenever MAX isn't a multiple of numProc. The remainder is never handed out. Slide 24's boundaries always end at exactly N.

Next time, from memory

Write the fair-split loop for N items over k threads.

for (j = 0; j <= k; j++) index[j] = (int) ((long) j * N / k); Thread j gets [index[j], index[j+1]).

How many threads for CPU-bound work, and why not more?

One per processor (availableProcessors()). Extra threads can't run at the same time; they only add creation and scheduling cost.

Why must every start() come before any join()? (lesson 1)

join() waits for that thread to finish. Joining before the next start() means the next thread doesn't begin until the previous one is done, so nothing runs in parallel.
