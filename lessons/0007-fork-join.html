Fork/Join

A task that splits itself in half until it is small, run by a pool whose idle threads steal work.

Your win today: you'll write the five lines that make a task split itself, and count lesson 6's primes twice as fast on 2 threads, without choosing any piece sizes. About 25 minutes.

Deck 2 slides 79–99 finish the deck's story. Lesson 6 ended with a question the slides never answered: how small should the pieces be? Fork/Join's answer is to stop choosing. Each task splits itself until it is small, and the pool shares the pieces out.

1 · Divide and conquer

Deck 2 · slides 79–81

Slide 80 is the whole idea, written as pseudocode:

solve(problem):
    if problem is small: solve it directly
    else:
        split it into independent parts
        fork a subtask for each part
        join all the subtasks
        combine their results

It's lesson 1's pattern (split, start, join, combine), but recursive: each half is split again, and again, until the pieces are small. A job of 10 million numbers with a base size of 1,000 is halved 14 times, into about 16,000 tasks of about 600 numbers each.

2 · Work stealing

Deck 2 · slides 82–83

The tasks run in a ForkJoinPool. It differs from lesson 5's pool in one way that matters (slide 82):

  • Each thread has its own queue. When a task forks subtasks, they go on that thread's queue.
  • A thread whose queue is empty steals a task from another thread's queue.

So with uneven work, the thread that got the cheap half of the primes runs out, steals part of the expensive half, and nobody sits idle. This is lesson 6's small-pieces fix, done automatically.

new ForkJoinPool() makes one thread per processor (slide 83). You can pass a number to choose: new ForkJoinPool(2).

Javadoc: the no-argument constructor “Creates a ForkJoinPool with parallelism equal to Runtime.availableProcessors()”. ForkJoinPool

3 · The task classes

Deck 2 · slides 84–91

You write a class that extends one of two types and override compute() (slide 84):

  • RecursiveTask<V>: compute() returns a V. Like lesson 5's Callable.
  • RecursiveAction: compute() returns nothing. Like Runnable. (Slide 84 writes RecursiveAction<V>, but it takes no type parameter; see the errata.)

Slides 88–90's sum, shortened:

class Sum extends RecursiveTask<Long> {
    static final int BaseBlockSize = 5000;
    // fields data, lb, ub and a constructor
    protected Long compute() {
        if (ub - lb <= BaseBlockSize) {
            long sum = 0;   // small: a plain loop
            for (int i = lb; i < ub; ++i) sum += data[i];
            return sum;
        }
        int mid = lb + (ub - lb) / 2;
        Sum left  = new Sum(data, lb, mid);
        Sum right = new Sum(data, mid, ub);
        left.fork();          // queue both halves
        right.fork();
        long rSum = right.join();  // wait, take result
        long lSum = left.join();
        return lSum + rSum;
    }
}

Here fork() is like submit: it queues the task and returns at once. join() is like future.get(): it waits and returns the result. Note that this is ForkJoinTask.join(), not Thread.join(); the name is reused. protected just means subclasses can see the method; copy it as written.

Slide 91 starts it with one call that waits for the whole tree and returns the top task's result:

ForkJoinPool fjPool = new ForkJoinPool();
long sum = fjPool.invoke(new Sum(f, 0, f.length));
mid = lb + (ub - lb) / 2 rather than (lb + ub) / 2: the second form can overflow int for huge arrays, the same trap as lesson 4's j * N.

4 · Never do this

Deck 2 · slide 87

left.fork();
long lSum = left.join();   // waits for left first...
right.fork();              // ...so right starts late
long rSum = right.join();

Joining left before forking right makes the halves run one after the other, at every level of the recursion. It's the same mistake as start(); join(); in one loop (lesson 1). I timed it with the exercise below: 2.83 s, exactly as slow as no threads at all (2.81 s). The correct order took 1.41 s.

5 · Quicksort

Deck 2 · slides 92–99

Slides 92–95 are the ordinary quicksort: rearrange a segment into a left part and a right part, then sort each part. You don't need the partition details for this module's parallel part. What matters is that the two parts are independent, so they can run as parallel subtasks (slide 96). Sorting returns nothing, so QuickSort extends RecursiveAction (slides 97–98):

QuickSort left  = new QuickSort(data, lb, i);
QuickSort right = new QuickSort(data, j, ub);
invokeAll(left, right);   // fork both, wait for both

invokeAll does the fork-both-then-join-both pattern in one call, so slide 98's extra left.join(); right.join(); afterwards is harmless but unnecessary. Slide 99: 10 million numbers in about 2.9 s on a dual-core machine.

Javadoc for invokeAll(t1, t2): “Forks the given tasks, returning when isDone holds for each task”. ForkJoinTask

Check yourself

Answer from memory, without scrolling up. You get one click per question.

In a ForkJoinPool, what does a thread do when its own queue is empty?

Work stealing (slide 82): an idle thread takes a task from another thread's queue. That's how Fork/Join keeps every core busy even when the work is uneven.

Which order of calls runs both halves in parallel?

Fork both before joining either. Joining left before right exists in the queue is slide 87's “never do this”: the halves run one after the other.

A Fork/Join task sorts an array in place and returns nothing. What does it extend?

RecursiveAction's compute() is void, like slide 97's QuickSort. It takes no type parameter, whatever slide 84 says.

Compared with lesson 6's fixed pool of 1,000-number pieces, what does Fork/Join remove?

You still need a pool, a small-enough base case and a combine step. What's gone is cutting the job up yourself: tasks split themselves, and stealing balances the load. In the exercise, both approaches took about 1.4 s on 2 threads.

Exam practice

Describe the Fork/Join framework and explain how work stealing improves on a pool with a fixed division of work. (6 marks)

A Fork/Join task solves a problem directly if it is small (below a threshold); otherwise it splits it into independent subtasks, forks them, joins them and combines their results, recursively. Tasks extend RecursiveTask<V> (returns a value) or RecursiveAction (no value) and override compute(). They run in a ForkJoinPool, by default one thread per processor. Each thread keeps its own queue of forked tasks; when its queue is empty it steals a task from another thread's queue. With a fixed division, a thread that gets less work finishes early and idles; with stealing it takes over part of a busy thread's work, so the load balances automatically without choosing piece sizes in advance. All subtasks must be forked before any is joined, or the parts run sequentially.

Marks are my estimate, not taken from your exam.
