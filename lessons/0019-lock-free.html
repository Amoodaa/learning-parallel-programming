Lock-Free Data Structures

Thread safety without locks: try the update, and if another thread got there first, try again. It's all built on one hardware instruction, compare-and-swap.

Your win today: you'll make a stack that 4 threads push and pop at the same time, using no locks at all. About 25 minutes.

Deck 7 (Non-Blocking Lock-Free Data Structures) questions everything since lesson 8. Every tool so far, synchronized, ReentrantLock, conditions and semaphores, makes a thread wait. This deck makes threads retry instead. You've already used one result of it: the tunnel's AtomicInteger in lesson 15.

1 · Pessimistic vs optimistic

Deck 7 · slides 2–8

Two definitions to learn word for word (slide 2):

  • Non-blocking: if one thread fails or is suspended, that does not cause another thread to fail or be suspended.
  • Lock-free: at each step, some thread can make progress.

A lock breaks both. If the thread holding it is paused, everyone waiting for it is stuck. Locking is pessimistic (slide 3): it always locks, even when no other thread would have interfered, and that costs time. The optimistic approach (slide 4) does the update anyway and then detects a collision: if another thread changed the data meanwhile, the update fails and the thread retries. Slide 5's argument: contention is usually low, so the update usually succeeds the first time. And when several threads do collide, one of them always wins, so something always makes progress.

Slide 6 reports Goetz's experiment with a random number generator built both ways. Under very high contention, locks did better, because the retries wasted time. At realistic contention, atomic variables did better.

Advantages (slide 7)Disadvantages (slide 8)

Priority inversion is when a high-priority thread waits for a lock held by a low-priority thread, so in effect it runs at the low priority. Without locks there's nothing to wait on, so it can't happen.

2 · Compare-and-swap (CAS)

Deck 7 · slides 9–13

CAS is a single, atomic hardware instruction (slide 9). It says: "if the variable still holds the value I expect, set it to the new value; otherwise, don't touch it and tell me I failed" (slide 10):

// cas(memWord, expectValue, newValue), all one atomic step
if (memWord == expectValue) {
    memWord = newValue;
    return true;
} else return false;

Because it can fail, it's always used in a retry loop (slides 11–12). Read the current value, compute the new one, and try to swap it in. If another thread changed the variable meanwhile, the CAS fails, so you read again and recompute:

int x0, x1;
do {
    x0 = x;              // read
    x1 = x0 + k;         // compute (the "speculative" step)
} while (!cas(x, x0, x1));   // swap in; retry if x changed

Compare lesson 8's lost update: x = x + 1 lost updates because another thread could write between the read and the write. CAS doesn't prevent that write. It detects it and refuses to overwrite. (Slide 12 is missing a ) after cas(x,x0,x1).) In Java, CAS is compareAndSet(expected, update) (slide 13).

3 · The atomic classes

Deck 7 · slides 14–24

java.util.concurrent.atomic has AtomicInteger, AtomicLong, AtomicBoolean and AtomicReference<V> (slide 14). All four have get, set, getAndSet and compareAndSet (slides 16–18). The number classes add ready-made retry loops (slide 15):

AtomicInteger n = new AtomicInteger(0);
n.incrementAndGet();  // ++n atomically; returns new value
n.getAndIncrement();  // n++ atomically; returns old value
n.decrementAndGet();  n.getAndDecrement();

Slide 19's Counter is lesson 8's counter with no synchronized at all. Slides 20–22 write inc() by hand with compareAndSet, the loop from section 2, to show what incrementAndGet does inside. (Slide 20 never creates the AtomicInteger: private AtomicInteger value; is null, so the first call throws a NullPointerException. It needs = new AtomicInteger(0).)

The limit (slides 18 and 24): an atomic class makes one variable safe. It cannot keep an invariant between two variables (lesson 8's x == y, or a stack's array and its size), because each CAS covers only one variable. Slide 24 also warns: atomic classes are mutable, so don't use them as replacements for Integer, or in anything used for hash codes.

4 · Two stacks

Deck 7 · slides 25–35

The spin-lock stack (slides 25–29). An array stack has an invariant between stack[] and size, which one CAS can't cover. Slide 26 builds a lock out of an AtomicBoolean:

while (true) {
    if (lock.compareAndSet(false, true)) {   // got it
        // ... push using stack[] and size ...
        lock.set(false);                     // release
        return true;
    }   // else: loop and try again ("spin")
}

Only one thread can switch false to true, so this is mutual exclusion. Be careful, though: it is still a lock. If the thread holding it is paused, every other thread spins forever. By slide 2's definition it is not non-blocking. It just waits by spinning instead of sleeping.

The lock-free linked stack (slides 30–35). Here the whole state is one reference, the head of a linked list, so CAS can protect it:

// push(item), slide 32
Node newHead = new Node(item);
do {
    oldHead = head.get();
    newHead.next = oldHead;
} while (!head.compareAndSet(oldHead, newHead));

// pop(), slide 33
do {
    oldHead = head.get();
    if (oldHead == null) return null;     // empty
    newHead = oldHead.next;
} while (!head.compareAndSet(oldHead, newHead));
return oldHead.item;

Each operation prepares the change privately, then swaps head in one CAS. If another thread moved head meanwhile, the CAS fails and the operation starts again with the new head. No thread ever waits for another, so this one really is lock-free. Slide 35 wraps it as a Stack. (Slide 34's head() calls head.get().item, which throws a NullPointerException on an empty stack.)

Check yourself

Answer from memory, without scrolling up. You get one click per question.

compareAndSet(5, 6) is called, but the value is now 7. What happens?

CAS only writes if the current value equals the expected one. On failure it returns false and the caller decides what to do: usually re-read and retry.

Why is CAS almost always inside a loop?

Failure means "someone else updated it since you read it". Re-read, recompute, and try again (slides 11–12).

Why can't an AtomicInteger for size alone make an array stack thread-safe?

A push must write stack[size] and increment size as one action. Atomic classes "are not suitable to maintain state invariants" (slide 18). Hence the spin lock, or the linked list whose whole state is one reference.

Is slide 26's AtomicBoolean spin-lock stack non-blocking?

Non-blocking means a suspended thread can't stop others (slide 2). A spin lock is still a lock: it waits by spinning instead of sleeping. The linked stack is different, because no thread ever waits for another.

Stuck? Hint

Section 4's code, adapted: Node here is immutable (final fields), so build new Node<>(x, oldHead) inside the loop. In pop, check for null inside the loop, because the stack can become empty between tries.

Stretch: break it on purpose

(a) Fix push but leave pop as it was. Does the checker see the difference? (b) Without running anything: why would a synchronized stack also pass, and what would it lose?

Solution (only after trying) 
void push(E x) {
    Node<E> oldHead, newHead;
    do {
        oldHead = head.get();
        newHead = new Node<>(x, oldHead);
    } while (!head.compareAndSet(oldHead, newHead));
}

E pop() {
    Node<E> oldHead;
    do {
        oldHead = head.get();
        if (oldHead == null) return null;
    } while (!head.compareAndSet(oldHead, oldHead.next));
    return oldHead.item;
}

(a) Yes. In my runs over 100,000 numbers were still popped twice: two threads read the same head and both "popped" it. (b) A lock makes it correct too, but it's then blocking: a paused thread holding the lock stops everyone, and every operation pays for locking even when there's no contention (slide 3).

Exam practice

Explain compare-and-swap and show how it implements a thread-safe counter without locks. (5 marks)

CAS(location, expected, new) is an atomic hardware instruction. If the location holds expected, it writes new and returns true; otherwise it changes nothing and returns false. Counter increment: read the current value v, then attempt compareAndSet(v, v + 1). If it fails, another thread updated the counter in between, so read v again and retry, until it succeeds. No update is lost, because a CAS based on a stale value always fails. No thread ever blocks, and among contending threads one CAS always succeeds, so the counter is lock-free.

Give two advantages and two disadvantages of lock-free data structures compared with locking. (4 marks)

Advantages: no deadlock, because there are no locks; no priority inversion; high performance at realistic contention and when threads access different items; a suspended thread can't block the others. Disadvantages: under high contention threads retry repeatedly, which wastes CPU and can cause liveness problems; they are hard to write correctly; they need hardware CAS; atomic variables cover only single variables, not invariants.

Marks are my estimate, not taken from your exam.

Define non-blocking and lock-free (slide 2).

Non-blocking: the failure or suspension of one thread can't cause the failure or suspension of another. Lock-free: at each step some thread can make progress.

Why must a semaphore-based buffer still use a lock around the list? (lesson 15)

The semaphores only count slots and items. Several producers (or consumers) can hold permits at once and would change the ArrayList at the same time.
